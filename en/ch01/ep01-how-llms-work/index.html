Learning objectives

By the end of this episode you will be able to

  1. Explain how an LLM produces its answer one token at a time, and how the chat template turns messages into what the model reads
  2. Count the tokens of Thai and English text and estimate the cost of a call
  3. Explain greedy, top-k, top-p, min-p and temperature, and pick a temperature that suits an agent’s task
  4. Use max_tokens and check finish_reason to know whether an answer was cut off
  5. Read a model name (size, MoE, instruct) and work out the memory at each quantization level
  6. Explain why the same model from different providers gives different results, and check the modality before sending an image

Three questions agent builders run into

Why does asking the same question twice give different answers? Why does Thai cost more than English? And why do some models break the moment you send them a picture? An agent builder doesn’t have to build an LLM, just as a driver doesn’t have to build the engine — but they do have to read the dashboard. This episode opens the dashboard gauge by gauge and answers all three questions with numbers from real lab runs.

An LLM answers one piece at a time

The textbook sums up how an LLM works as one pipeline (Roitman 2026, sec. 1.1; Vaswani et al. 2017): text is cut into small pieces (tokens) → the model reads all of them at once → gives a probability to every token that could come next → picks one, appends it to the input and runs again.

It is like the next-word suggestions on a phone keyboard, where we keep tapping the suggestion until the sentence is done. Everything in this episode comes from two parts of this pipeline: the pieces the text is cut into and how the next piece is chosen.

Tokens and the chat template

A token is a piece of text the model reads; the thing that cuts text into tokens is the tokenizer. The textbook explains that cutting into characters makes sequences long and expensive, while cutting into words means the model can’t take words it has never seen — so text is cut into pieces in between (Roitman 2026, sec. 1.2; Sennrich et al. 2016). Like Lego bricks: a common word such as “the” is a single brick, while rarer words are built from smaller ones — “unhappiness” might become “un” + “happiness”.

The textbook recommends measuring fertility, the number of tokens per word. High fertility means the tokenizer covers that language poorly, and since price is counted in tokens, Thai costs more. Every model has its own tokenizer, so the same text can count differently.

When we call a model through an API we send a list of messages, each with a role saying who is speaking (system = the standing instructions, user = the user, assistant = the model). But the model can only read one line of tokens, so the chat template joins the messages into a single string and separates the parts with special tokens, like a play script with the speaker’s name before each line. The textbook points out that a dedicated token for calling a tool is more reliable than having the model write “now I will call a tool”.

In Lab 1: we send the single letter a, yet usage counts more than one input token. The extra is what the chat template adds — 13 tokens on every call — and we pay for them too.

Probabilities and greedy

Each time it produces a new token, the model doesn’t hold just one answer; it gives a probability to every token it knows, summing to one. The textbook’s example is “The capital of France is”, where the token “Paris” gets 0.92 (Roitman 2026, sec. 1.12). The simplest way to choose is greedy: always take the top token — like always ordering the best-selling dish: never a miss, but never anything new. The textbook warns that it tends to produce repetitive, bland text.

The API doesn’t return probabilities directly but logprobs (the log of the probability), which convert back with \(p = e^{\text{logprob}}\); for example a logprob of \(-0.28\) is \(e^{-0.28} \approx 0.756\).

Bounded sampling: top-k, top-p, min-p

For variety we sample by probability. Sampling from every token, though, can let an odd word slip in, so we cut off the tail first. The textbook describes three ways; think of picking finalists in a singing contest.

The textbook’s example: after “2 + 2 =”, the token “4” has almost everything; top-k of fifty would keep 49 wrong answers, while top-p keeps just “4”. After “I enjoy eating”, many foods are plausible: top-k of five is too narrow, but top-p widens the pool by itself. So top-p and min-p adapt to the model’s confidence; top-k doesn’t (Holtzman et al. 2020; Nguyen et al. 2025).

Temperature: the boldness knob

Before sampling we can also reshape the probabilities with temperature (\(T\)). In Lab 2 we write it ourselves from the probabilities \(p_i\):

\[ p_i^{(T)} = \frac{p_i^{1/T}}{\sum_j p_j^{1/T}} \tag{1.1}\]

\(T < 1\) makes the top tokens even stronger (confident), \(T > 1\) pulls everything closer together (bold), and \(T \to 0\) is greedy. The textbook’s example is “Once upon a time”: at \(T = 0.3\) the model tells a typical tale of a just king, while at \(T = 1\) rivers flow backwards and fish learn to fly. It recommends \(T = 0\) for code and maths, 0.7 for factual work, and 1–1.2 for creative work.

ImportantFor agents

When the model has to write a tool name and its arguments correctly, use a low temperature. This answers the first question: asking again gives a different answer because the model samples its tokens.

In Lab 2 (Gemma’s real probabilities through a pinned provider): “The capital of France is” → Paris almost 1.00 · “I enjoy eating” → pizza 0.756, food 0.115, everything 0.105 · at \(T = 2\) pizza drops to 0.485 · top-k 5 even keeps “Paris” in Chinese and Japanese, while top-p 0.95 keeps only Paris · setting temperature=0 on the API gives pizza 10 times out of 10

The context window and max_tokens

The context window is the maximum number of tokens a model can read and write at once; Gemma 4 26B in the labs has 262,144. The textbook calls it the agent’s working memory (Roitman 2026, sec. 18.2): every token in it costs money and time, and the model can’t see anything outside it — like a desk where you can only read the papers on it; however good the books in the library are, they don’t help unless you bring them to the desk. On the desk are the standing instructions, a conversation history that keeps growing, and room left for the answer, so count tokens before every call.

The answer has its own ceiling, max_tokens. If it is reached before the model finishes, the answer is cut off mid-sentence and finish_reason is "length" instead of "stop".

In Lab 1: a thousand questions cost only about a cent, but an agent calls many times and resends its history, so the number grows fast. With a low max_tokens the answer really is cut off, with finish_reason = "length" — an agent must check it every time.

Reading a model name

A name on OpenRouter such as google/gemma-4-26b-a4b-it reads piece by piece.

MoE is like a hospital with many specialists where each patient sees just two. An instruct model is like someone who has read many books and then trains on the job as a help-desk assistant — so agent work should use instruct versions.

Quantization and providers

A 26-billion-parameter model stored at 16 bits (2 bytes) per number needs about 52 GB of memory. The textbook says serving almost always uses quantization: fewer bits per number (Roitman 2026, sec. 1.14) — like rounding 3.14159 to 3.14, or shrinking a RAW photo to a JPEG: the file gets much smaller, but the eye can hardly tell.

\[ \text{memory (GB)} \approx \text{parameters (billions)} \times \frac{\text{bits}}{8} \tag{1.2}\]

The companies that run a model for us behind an API are providers. The same Gemma name on OpenRouter has 15 of them: some run it at bf16, some at fp8 or fp4, and some don’t say; prices and context windows differ too.

In Lab 3 (2026-11-09): input prices differ almost fourfold, some providers offer only 131,072 tokens of context, half of the others, and asking “I enjoy eating” through 4 providers gives different results — Google puts pizza at 0.76, Darkbloom puts food at 0.77. So pin the provider while testing an agent, or today’s and tomorrow’s results might come from different providers.

Modality: what a model accepts

A kind of data is called a modality: text, images, audio, video or files. Models don’t all accept the same ones, and input and output are separate: Gemma 4 can look at a picture but can’t draw one, because almost every model answers in text. This textbook deliberately focuses on text-in, text-out models, so the numbers below come from OpenRouter’s model list.

Images become tokens too, so they take up context and cost money, and the model name doesn’t always tell you the modality. If an agent’s tool fetches an image for the model, check the modality first, or the agent will break halfway.

In Lab 3: of 461 models on OpenRouter, 137 accept text only. A one-sentence question with a chart used 278 input tokens, because the image became tokens (the chart’s numbers are made up for teaching).

Review questions

  1. Why do a Thai and an English sentence with the same meaning use different numbers of tokens, and do different models count the same?
  2. You send a very short message, but usage counts more input tokens than expected. Where does the extra come from?
  3. After “2 + 2 =”, why is top-p better than top-k 50?
  4. If an agent must call tools correctly every time, how should you set the temperature, and why?
  5. What does finish_reason = "length" tell you, and what should an agent do about it?
  6. About how much memory does Gemma 4 26B need at fp8, and how do you work it out?
  7. Why pin the provider while testing an agent?
  8. If an agent’s tool fetches an image for the model, what must you check first?

Further reading

Not needed for the labs, but useful for going deeper. In the order of this page.

  • The original Transformer: the paper every LLM in this course descends from (Vaswani et al. 2017)
  • Tokens: a video that builds a GPT-style tokenizer from scratch (Karpathy 2024) and the original BPE paper (Sennrich et al. 2016); for chat templates see the Hugging Face docs (Hugging Face 2025a)
  • Decoding: a hands-on comparison of greedy, beam search, top-k and top-p with code (Platen 2020); where top-p (Holtzman et al. 2020) and min-p (Nguyen et al. 2025) come from
  • Instruction-tuned models: how a base model is trained to follow instructions (InstructGPT) (Ouyang et al. 2022)
  • Mixture of experts: an accessible explainer (Hugging Face 2023) and the Switch Transformer (Fedus et al. 2022) and Mixtral (Jiang et al. 2024) papers
  • Quantization: an overview of the methods in Hugging Face (Hugging Face 2025b) and the paper that made 8-bit inference widespread (Dettmers et al. 2022)
