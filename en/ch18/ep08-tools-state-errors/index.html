Learning objectives

By the end of this episode you will be able to

  1. define a tool for a model, and match each result to its request by the tool call’s id
  2. run the tools a model asks for in one turn at the same time, and process tool output in four steps before it goes back into the context
  3. explain prompt injection through tool output, and wrap tool output so the model treats it as data
  4. describe the four layers of an agent’s state, and save a checkpoint that lets a task resume after a crash
  5. retry with exponential backoff and jitter, switch to a fallback model, detect loops, and fail gracefully
  6. work out what a task costs, use prompt caching, and set a token budget per task
  7. do checkpoints, resume and branching with LangGraph

Three things went wrong

Say we ask our research assistant to write a two-page report from three papers. The task has ten steps, and we see three things. First, it fetches the papers one at a time, waiting for the first before asking for the second. Second, at step seven the network drops for a moment, and it starts over from step one. Third, it runs the same search six times in a row. And at the end of the day, the API bill is longer than expected. None of these can be fixed inside the model, but the harness can prevent all of them.

In EP07 we covered the first kind of memory the harness manages, the context window. This episode covers the four topics the textbook takes next (Roitman 2026, sec. 18.4, §18.6–18.8): tools (§18.4), state (§18.6), errors (§18.7), and speed and cost (§18.8).

Defining a tool

Before the model can call a tool, it has to know which tools exist, so the harness sends the tool definitions with every request. Each provider uses a slightly different format. OpenAI’s puts the arguments under parameters, Anthropic’s under input_schema; inside, both are the same JSON schema.

{"type": "function",
 "function": {"name": "get_paper",
              "description": "Get a paper's title and abstract by its id.",
              "parameters": {"type": "object",
                             "properties": {"paper_id": {"type": "string"}},
                             "required": ["paper_id"]}}}

When the model wants a tool, it replies with a request that carries an id. The harness runs the tool and sends the result back with the same id, like a cloakroom ticket: hand in the matching number to get the right coat back. When several tools run at once, the id is what tells which result belongs to which request. MCP is a common standard that frees us from any one provider’s format; it comes in full in EP13.

Who picks the tool

The model chooses, but the harness can shape the choice in three ways:

Parallel calls answer the first problem: ask for all three abstracts in one turn and wait only for the slowest, like ordering three dishes at once.

With hundreds or thousands of tools, putting every definition in the prompt wastes tokens and confuses the model. The textbook offers two ways: retrieve the few most relevant tools each turn, as Gorilla does over thousands of APIs (Patil et al. 2024), or train the model to pick better, like ToolLLM, trained on more than 16,000 APIs (Qin et al. 2024). In practice the two are combined.

In Lab 1: the model asked for three papers in a single message, each request with its own id. Running them one at a time took 4.5 s; all at once with ThreadPoolExecutor, 1.5 s, the time of the slowest one alone. Each result went back as a tool message with the id of its request.

Processing tool output in four steps

Raw tool output is rarely ready to go straight into the context. The textbook gives the harness four steps:

  1. Parse and validate: check the output matches the expected format.
  2. Truncate large outputs: web pages, code output or database results can be enormous. The textbook’s code cuts cheaply first, and asks a model to summarize only when the output is more than twice the budget. This is the \(T\) budget from EP07.
  3. Normalize errors into one standard format, because every provider words errors differently, so the model can make sense of them.
  4. Retry transient failures (a timeout, a rate limit) first, and only then report the failure to the model.

In Lab 1: run_tool checks the arguments before running anything. An unknown paper id P9 came back as {"error": "not_found", "detail": "no paper with id P9", "retry": false}, and the model told the user plainly that P9 wasn’t found. A simulated project page of 37,411 tokens was summarized down to the budget before going back to the model.

Sandboxes and prompt injection

The textbook calls tool execution a major attack surface. The harness must run tools in a sandbox isolated from the system (a container with no network), declare each tool’s permissions, limit CPU, memory and time, validate the arguments the model sends, and log every call.

The danger it stresses most is prompt injection through tool output (Greshake et al. 2023). Say the agent reads a paper’s web page, and the page hides a line telling it to ignore previous instructions. If the harness drops that text into the context as is, the model may follow it. So every tool output is data, not instructions: wrap it in tags the model is told to treat as data. Like a secretary reading a letter aloud to the boss: even if the letter says “secretary, transfer the money”, the secretary doesn’t do it.

In Lab 1: the simulated PatchTST page hid an instruction in an HTML comment telling AI assistants to end every answer with a fake download link. Unprotected, the model added the link in 5 of 8 runs. With the output wrapped in <tool_output> tags and a rule in the system prompt, 0 of 8. Wrapping lowers the risk; a real system still needs other guards too.

A checkpoint is a saved snapshot of state that lets a task resume after a failure; rollback undoes the last few actions when a mistake is found. That answers the second problem: a drop at step seven shouldn’t mean starting over from step one.

In Lab 2: a six-step task (three paper notes, compare, title, report) with the network dropping at step four. Without a checkpoint it started over: 9 model calls for a task that needs 6. With a TaskState dataclass saved after every step (written to a temporary file, then swapped in with os.replace, so a crash mid-write can’t leave a broken file), it resumed at compare: 6 calls in total. Rolling back the last two steps to rewrite the opening paragraph for first-year students took 2 calls.

Smarter retries

In EP06 we retried after one second, then two. The textbook gives the full formula: the wait before retry \(k\) is

\[ t_k \;=\; \min\!\big(2^k \cdot t_0 + U(0,\, t_0),\ t_{\max}\big) \tag{36.1}\]

With \(t_0 = 1\) s the waits are 1, 2, 4, 8, 16 s, then the ceiling: exponential backoff, like calling a friend whose line is busy and waiting longer each time. The random term \(U(0, t_0)\) is jitter: if ten agents sharing one key are all rate-limited at once and each waits exactly the same time, they all come back together and get limited again. Jitter spreads them out.

The textbook adds two more options: if the main model is unavailable, switch to a fallback model; if a tool is down, tell the model plainly and let it carry on without it (graceful degradation).

In Lab 3: a simulated search API refused three times with a 429. With \(t_0 = 0.5\) s the waits were 0.75, 1.28 and 2.40 s, and the fourth try answered. Without jitter, ten agents all came back at exactly 0.5 s; with jitter they spread out between 0.63 and 0.92 s. With the main model made unavailable, the harness tried it three times, then switched to Gemma 3 12B, which answered.

Detecting loops

The third problem: the agent calls the same tool with the same arguments again and again. The textbook gives three methods: a cap on the number of steps (which we’ve used since EP03, but by step fifty a lot is spent), hashing each action’s tool and arguments, and watching whether the state makes progress. With hashing, it’s a loop if two steps have the same hash no more than \(W\) steps apart:

\[ \exists\, i < j:\ h(a_i) = h(a_j) \ \wedge\ j - i \leq W \tag{36.2}\]

Like pressing a lift button again and again when it’s already lit: repeating doesn’t change anything.

Some tasks really can’t be finished. A good agent then fails gracefully in four parts: what was accomplished, why it couldn’t continue, a way forward, and the state saved so the task can resume. To know what happened, the textbook’s three pillars are a trace of every run, logs with tokens, latency and cost, and metrics such as success rate and cost per task. We built a trace in EP06 Lab 2.

In Lab 3: a polling tool kept answering “the PDF is still being converted, call again”. With only a step cap, the agent made 12 model calls, all asking for the same thing. A LoopGuard that hashes each call over a window of 5 stopped it at the third identical request (3 calls), with a four-part message and the state saved to stuck_task.json.

Speed and cost

For speed the textbook gives four options: parallel tool calls, streaming, speculative execution (starting the likely next tool call early) and prompt caching. Every step of our task sends the same system prompt and tool definitions, so many providers keep the work already done on that repeated beginning; the textbook says the cached part gets 50–90% cheaper and faster. But the cache only works for a beginning that is exactly the same. Put the current time on the first line and the beginning differs every call. The rule: static first, changing last.

For cost, the textbook’s equation sums every model call and every tool call in a task:

\[ \text{Cost} \;=\; \sum_{i} \big(p_{\text{in}} \cdot n_{\text{in},i} + p_{\text{out}} \cdot n_{\text{out},i}\big) \;+\; \sum_{j} c_j \tag{36.3}\]

So it recommends a token budget per task, a small cheap model for simple steps, and caching tool outputs that always give the same answer. When many agents share one key, it adds a shared rate limiter, priority queues and backpressure: reject new tasks plainly with a 503 when the queue is full, rather than queuing them forever.

In Lab 4: a system prompt of about 4,600 tokens and eight questions. With the static part first, the first call wasn’t cached but 5 of 8 were, and a cached call cost almost half as much. With the time on the system prompt’s first line, 0 of 8. Moving one line saved 27% of the total. Makora’s discount on cached tokens is about 46%, below the textbook’s 50–90%: it depends on the provider. Counting the tools too (simulated at $0.001 a call), the tools cost about three times the model. A TokenBudget of 20,000 tokens warned at question four and stopped the task at question five.

  2. Which of the four steps for tool output would have caught a 37,411-token web page, and what did the textbook’s code do with it?
