Models do not answer the same way every time, so your own run may differ from this page.

From the theory video: the model chooses the tool, but the harness runs it and processes the result before it goes back into the context (§18.4)

What you’ll learn

  1. Define a tool in OpenAI’s format (parameters = a JSON schema) and let the model ask for three papers in one turn (parallel tool calls)
  2. Run them one at a time vs all at once — and time it
  3. Send each result back with its tool_call_id
  4. run_tool: validate the arguments and normalize errors into one format
  5. An output bigger than its budget: cut it to fit, or have the model summarize it
  6. Prompt injection through a web page: unprotected vs wrapped in <tool_output> — 8 runs each, and we count

The papers, the web pages and how long the tools take are simulated data written for teaching. The tool calls, the answers and how many runs were injected come from real runs.

Source: Haggai Roitman, The Hitchhiker’s Guide to Agentic AI, §18.4 — CC BY-SA 4.0

1. Calling Gemma through OpenRouter

Why google/gemma-4-26b-a4b-it — it can call tools and ask for several tools in one turn (parallel tool calls), which this lab needs. Its tokenizer is open to download too, so we can count tokens on our machine exactly as the model does (EP07)

Why the provider is pinned to Makora (not DeepInfra as in EP07) — we tested every provider serving this Gemma 4 (2026-11-17): Makora is the only one that reports cached_tokens steadily, which Lab 4 needs to show prompt caching, and it asked for three tools in one turn every time · the whole EP uses the same provider, so the results compare

Not free, but very cheap: Makora charges USD 0.09 per million input tokens and USD 0.28 per million output tokens — at the end of the lab we add up the real cost · The :free version doesn’t work (tested 2026-11-17: 3 out of 3 calls got 429 “rate-limited upstream”)

import json, os, time
from concurrent.futures import ThreadPoolExecutor
from openai import OpenAI

def load_key():
    try:  # Google Colab Secrets
        from google.colab import userdata
        return userdata.get("OPENROUTER_API_KEY")
    except ImportError:
        pass
    from dotenv import load_dotenv
    load_dotenv()
    return os.environ["OPENROUTER_API_KEY"]

client = OpenAI(base_url="https://openrouter.ai/api/v1", api_key=load_key())
MODEL = "google/gemma-4-26b-a4b-it"
PROVIDER = {"order": ["makora"], "allow_fallbacks": False}
EXTRA = {"reasoning": {"enabled": False}, "provider": PROVIDER}

USAGE = {"in": 0, "out": 0}

def chat(messages, **kw):
    reply = client.chat.completions.create(model=MODEL, messages=messages, extra_body=EXTRA, **kw)
    USAGE["in"] += reply.usage.prompt_tokens
    USAGE["out"] += reply.usage.completion_tokens
    return reply.choices[0].message

5. run_tool: validate the arguments, normalize errors

Textbook §18.4.3: raw tool output isn’t ready for the context — parse & validate and normalize errors The model sends its arguments as text: they may be malformed, missing a field, or ask for a paper that doesn’t exist — the harness must not crash with them

def run_tool(call):
    try:
        args = json.loads(call.function.arguments)
    except json.JSONDecodeError:

### Summary of PatchTST (2023) Project Page

**Core Methodology**
PatchTST is a time-series forecasting model that utilizes a "patching" mechanism. Instead of processing individual time steps, the model splits each series into **patches of 16 steps**. Additionally, the architecture is designed to handle each channel within a multivariate series independently.

**Performance Overview**
The provided data contains extensive error metrics across several datasets (ETTh1, ETTh2, ETTh3, and ETTh4) at various forecasting horizons (96, 192, 288, and 384). The results are reported using two primary error measurements:
*   **MSE** (Mean Squared Error)
*   **MAE** (Mean Absolute Error)

**Key Data Observations**
While the page contains a large volume of repetitive experimental results, the following patterns can be identified across the ETTh datasets:

*   **ETTh1 (Horizon 96):** MSE typically fluctuates between approximately **0.300 and 0.396**, with MAE ranging between **0.350 and 0.446**.
*   **ETTh2 (Horizon 192):** MSE typically fluctuates between approximately **0.301 and 0.397**, with MAE ranging between **0.351 and 0.447**.
*   **ETTh3 (Horizon 288):** MSE typically fluctuates between approximately **0.302 and 0.398**, with MAE ranging between **0.352 and 0.448**.
*   **ETTh4 (Horizon 384):** MSE typically fluctuates between approximately **0.303 and 0.399**, with MAE ranging between **0.353 and 0.449**.

The results demonstrate consistent performance levels across the various testing iterations provided in the dataset.
