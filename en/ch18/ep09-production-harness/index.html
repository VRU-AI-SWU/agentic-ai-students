Learning objectives

By the end of this episode you will be able to

  1. read Listing 18.1, the textbook’s production harness in one file, and say what each of its five parts does
  2. give every part of the context a budget, and trim history without leaving a tool result behind without its request
  3. run tools without trusting them: approval, a time limit, retries with backoff, and a cap on the output
  4. catch an agent that repeats itself, and explain what a hash-based loop check can and can’t see
  5. test a harness without calling a model, with a mock LLM, unit tests and broken inputs
  6. keep prompts as versioned files, and replay saved tasks to catch a regression
  7. build the same harness with LangChain middleware, and say when to use a framework and when to build your own

Parts on the garage floor

Over EP07 and EP08 we collected every part of the harness: the context budget, running tools, retries, catching an agent that loops, and checkpoints. But car parts laid out on the garage floor are not a car you can drive. This episode answers two questions: how do all these parts fit into one program, and once it’s built, how do we know it works before we hand it to anyone else?

The textbook answers the first with Listing 18.1, a complete harness in one Python file, and the second with five ways to test an agent (Roitman 2026, sec. 18.10). Our running example is the research assistant from EP07–EP08: it searches a small paper library, reads abstracts, and saves a report, but only after a person approves.

Listing 18.1: one file, five parts

A ToolDefinition has five fields. Three go to the model: name, description and the JSON schema of its parameters. Two the model never sees: the Python function that does the work (handler), and requires_approval, which says whether a person must say yes first.

ContextManager: a budget on every message

The listing splits the context window into five shares:

Every time a message is added, the history is checked against its share. Over budget, the oldest message goes first, but the first message (the user’s question) always stays. And one detail matters a lot: if a dropped message asked for tools, every tool result that follows it must go too. A tool result left behind without its request makes the whole request invalid for the API. Before each model call, a preflight check adds up the system prompt, the tool definitions and the history and compares them with the window minus the reserved share.

In Lab 1 we counted tokens with Gemma’s own tokenizer instead of the listing’s tiktoken for GPT-4o, as the textbook’s summary says: count with the tokenizer of the model you actually use. In Lab 2 a unit test trimmed a small history and confirmed that what was left was the question, the later request and its result: the first request left together with both of its results.

ToolExecutor: run tools without trusting them

Every tool request passes through four steps:

  1. Unknown tool → an error message back to the model, not a crash.
  2. Approval: if the tool requires_approval, ask a person first; if they say no, the model gets “Action rejected by human reviewer.” and finds another way.
  3. Run with a time limit (30 s); on a timeout or an error, wait and try again, 1 s then 2 s, at most three attempts. The textbook puts retries at the tool level, because tools fail more often and usually recover on a second try.
  4. Cap the output at 2,000 tokens, with a note saying it was cut.

Every way out is a text message back to the model; none of them crashes the program.

LoopDetector: a fingerprint per action

For every tool call, the detector takes an MD5 fingerprint of the tool’s name and its arguments (with sorted keys) and keeps the last five. The same fingerprint twice in that window → the run stops with a polite message.

In Lab 2 testing with broken inputs found three things in the book’s code. A reworded search (“time series transformer” vs “transformers for time series”) is not a loop, because one different character gives a different fingerprint, though the textbook says the check catches near-repeats too. The loop check runs after the tools, so a repeated save_report had already run twice before the detector stopped it. And half-finished JSON arguments crashed run(), because the loop check parses the arguments again without a try; we fixed it as SaferHarness.

AgentHarness.run: the whole ReAct loop

Each run gets a short run_id stamped on every log line, so one run can be followed through mixed logs. The tools a model asks for in one turn run at the same time with asyncio.gather. And there are three special exits, each a polite message: the context is full, the agent is stuck in a loop, or it reached 50 iterations.

In Lab 1 the research assistant searched, then asked for three read_paper calls in one turn: “3 tool(s) done in 1.5s”, not 4.5 s. It asked for approval before save_report, and finished in 4 rounds for about $0.0003. When we said no, in some runs the model asked again with the same arguments and the LoopDetector stopped it; in others it gave its summary in the chat instead.

In Lab 2 the whole harness passed four checks against a mock LLM in under half a second, with no API key and no cost. A tool that always fails was tried three times (3 s), and one that hangs timed out three times (4.5 s), before the model got an error message; the program never crashed.

Prompts are code

One short line in the chapter summary: prompts should be version-controlled, tested, and assembled from components. One changed sentence in a system prompt can change the agent’s whole behaviour.

In Lab 3 the system prompt was built from part files (role · rules · cite · format), with an id made of the version and a hash of its text. Five real tasks were recorded with v1, which read the right papers but never cited one. Replayed with v2, which adds “Always cite paper ids like [P2].”, all five improved and nothing got worse, at about the same cost. A “cheaper” v3 that answers in one sentence cut output tokens by about a third, but two tasks regressed: one cited both papers in a single bracket, [P1, P4], which our checker didn’t count, and one answered without reading a paper at all. Reading the traces told a real regression from a checker that needed fixing, and in one of our runs v3 regressed only one task, so replay more than once before you decide.

Framework or build your own

The textbook compares the main frameworks (Roitman 2026, sec. 18.9) and gives a rule of thumb. Use a framework when you’re prototyping, when your use case fits its abstractions, or when you need to integrate many tools quickly. Build your own when you have strict latency or cost requirements, when the framework’s abstractions leak in ways that cause bugs, when you need fine-grained control over the context, or when the harness is what sets your product apart.

In Lab 4 LangChain made the same four model calls as our harness. Its default token count is an estimate that was off both ways (18 vs 14 tokens on an English sentence, 14 vs 24 on a short JSON), so we passed in Gemma’s tokenizer. With retry listed before loop_detector, reading the missing paper P9 was called a loop on the very first try, because the retry passed through our detector a second time; in the other order it tried three times and the model said P9 doesn’t exist. No line was wrong, only the order in the list.

One more thing both harnesses showed: after we rejected save_report, in some runs the model’s final answer said the report had been saved, though nothing was. So a harness should check the system’s real state, not take the model’s word for what it did.

Terms in this episode

Lab

The paper library and the tools in the code are simulated for teaching; every model output in the videos is from a real run. Your own run may differ a little, for example in what the model does after a rejection, or whether v3 regresses one task or two.

Review questions

  1. Why must a tool result leave the history together with the request that asked for it?
  2. Which of the ToolExecutor’s four steps would stop a model from saving a file you didn’t approve, and what does the model get instead?
  3. Why did a reworded search slip past the LoopDetector, and why did a repeated save_report run twice before it was stopped?
  4. What can a mock LLM test that a real model can’t, and what can’t it test?
  5. In Lab 3, which v3 regression was a real change in behaviour, and which one needed a better checker?
  6. Why did swapping two middleware in LangChain turn a missing paper into a “loop”?
  7. After a rejection, why should a harness check its own state rather than the model’s final answer?
