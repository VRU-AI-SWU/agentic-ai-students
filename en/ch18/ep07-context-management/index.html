The agent that forgot its first instruction

Picture this: we’ve been talking with a research assistant agent since nine in the morning. Our very first message said clearly: “Answer in Thai, and cite a paper every time.” Along the way we pasted in papers one by one, twelve of them. By eleven the agent answers in English, with no citations at all. The strange part: the log doesn’t show a single error. This episode explains what happened, and what the harness must do so it never happens again.

The agent harness

The textbook calls the structure wrapped around an LLM the agent harness. It turns the model from a text completer that remembers nothing into an agent with goals, many steps and tools (Roitman 2026, sec. 18.1). The model on its own is just a function from tokens to tokens: no memory, no API calls, no sense of time. So the textbook compares the harness to an operating system that gives the model a body.

The work splits cleanly. The thinking is the model’s; the harness handles tool calls, memory, message passing and logging every step. In our research assistant, Gemma does the thinking, but the harness calls search_papers, keeps the conversation and keeps the trace (EP06). The first piece of memory the harness must manage is the context window.

The context window is a desk

The context window is the agent’s working memory. Think of a desk: the model can read only the papers on the desk. A paper that isn’t on it, however important, is invisible to the model. And every paper on the desk has a cost: every token sent costs money and adds waiting time. Deciding what goes on the desk is one of the most consequential engineering decisions in agent design (Roitman 2026, sec. 18.2).

The context budget

The textbook writes the desk’s budget as one equation. The maximum context length \(C\) must hold five parts:

\[ C \;\geq\; S + M + T + H + R \tag{7.1}\]

The problem: \(C\) is fixed, but \(H\) keeps growing, and sometimes a tool returns a huge result at once, like a whole web page. The first approach is a fixed budget, like splitting a salary into envelopes. The textbook’s example: \(S\) 10%, \(M\) 20%, \(T\) 10%, \(H\) 50% and \(R\) 10%. Simple and predictable, but it wastes space when an envelope isn’t full. The other approach is a dynamic split every turn, which in practice means filling the most important parts first, then compressing or cutting the less important ones.

The silent truncation trap

Many APIs, given input longer than the context, quietly drop part of it, from the middle or from the beginning. The textbook calls this silent truncation. The system prompt may be lost, earlier instructions forgotten, or the model may hallucinate from the missing data, with no error signal at all. In our research assistant, the first message, the one saying “answer in Thai and cite papers”, is exactly what was cut.

ImportantThe textbook’s rule

Count tokens before every call, and handle overflow explicitly. Never let the API decide for you.

In Lab 1: we sent a conversation of about 270,000 tokens three ways. The pre-flight check stopped it before sending; sending it as is gave a clear 400 error; but OpenRouter’s middle-out option came back normally, 200 OK, while over 90,000 tokens from the middle were gone, so the model said there was no due date in the data. The harness caught it by comparing its own count before sending with the number of tokens the API said it really saw.

Compress the history ① summarize

When the history outgrows its budget, the harness must shorten it without losing what matters. The first approach summarizes the oldest \(k\) messages into one paragraph, placed before the recent messages, which stay word for word:

\[ H' \;=\; \text{Summarize}(H_{1:k}) \,\|\, H_{k+1:n} \tag{7.2}\]

Like not replaying a week of lecture recordings, but reading a one-page summary. The first ten messages of our research assistant might become “The user studies transformers for time series, wants answers in Thai with citations, and has read two papers.” The textbook says a summary is usually 5–10× shorter than the original, and a smaller, cheaper model can do the summarizing.

Compress the history ② keep what matters

The second approach doesn’t summarize; it chooses what to keep. The textbook offers two ways:

  • Selective retention: score each message by its relevance to the current question plus its recency, and keep the top \(k\). Measuring relevance needs tools we’ll meet in the RAG episodes.
  • Importance-weighted truncation: give each message a weight \(w_i\) (user corrections and tool results weigh more, small talk less) and keep the set with the largest total weight that fits the budget:

\[ \max_{\mathcal{K}} \sum_{i \in \mathcal{K}} w_i \quad \text{subject to} \quad \sum_{i \in \mathcal{K}} |m_i| \leq B_H \tag{7.3}\]

Like packing a suitcase with a 20 kg limit: what’s most worth its weight goes in first. The textbook says this is a 0/1 knapsack problem, solved greedily by sorting messages by \(w_i / |m_i|\).

Pinning saved the task, but the later correction was still lost. Importance weights kept every instruction, but one long note didn’t fit: 5 of 6. Summarizing the old part, from 532 tokens to 156, got all 6, like the full history, with less than half the tokens.

Recursive context decomposition

Every method so far accepts the same constraint: everything must fit in one window. The textbook describes an idea that rejects it: a recursive language model (RLM), where the model calls itself on one part of the data at a time (Roitman 2026, sec. 18.2.5).

Like a lecturer facing a six-hundred-page thesis who has each teaching assistant summarize one chapter, then combines their notes. Why does it help? The textbook’s answer is context rot: a model’s accuracy drops as the context grows, even with a 128K-token window. Keeping each call short and focused avoids it. The textbook cites research where a recursive GPT-5-mini beat plain GPT-5 on difficult long-context benchmarks, while being cheaper per query.

In Lab 3: a research group’s meeting notes for a whole year, 52 weeks and 8,243 tokens, hide three decisions to drop a paper. We set a budget of 1,500 tokens per call (an assumption for this lab; the document would fit Gemma’s real window). Cutting it to fit and sending once saw only the start and found just one decision. The textbook’s recursive_summarize built a tree two levels deep, 15 calls, the largest 798 tokens, never over budget. But in the first run P04 had no week, every time, because the sub-chunks had no ## Week 27 heading line. Carrying the heading into every chunk found all three with their weeks. Each small chunk must make sense on its own.

Prompt architecture

The textbook says the prompt is the main channel through which the harness talks to the model: it should be modular, composable and versioned (Roitman 2026, sec. 18.3). A production system prompt usually has four sections, identity, capabilities, constraints and output format, with blanks filled in at run time, such as the agent’s name, the tool list or today’s date.

The harness doesn’t keep the prompt as one block of text; it assembles it fresh every call from five blocks:

\[ \text{Prompt} \;=\; \text{Concat}(\text{System},\ \text{Memory},\ \text{Tools},\ \text{History},\ \text{Query}) \tag{7.4}\]

Like Lego: to change one piece, swap only that piece, and each piece has its own version number. Few-shot examples count against the budget too: the textbook suggests choosing only examples similar to the current question, within the \(M\) budget. Tool descriptions we wrote in EP06 Lab 1; what’s new here is including only the tools relevant to the task at hand, to save tokens and confuse the model less.
