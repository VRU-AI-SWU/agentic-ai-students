Learning objectives

By the end of this episode you will be able to

  1. explain how a skill differs from a tool and an agent, and name a skill’s five parts
  2. compare three ways to load skills: static, dynamic discovery with a skill router, and hierarchical composition
  3. write a skill as a SKILL.md folder, then load it, activate it and check its guardrails in code
  4. write a router that picks skills from their names and descriptions, and explain why a vague description makes it miss
  5. resolve a skill dependency graph with version checks, and build a skill library that learns, Voyager-style
  6. use the same skills with deepagents, and explain progressive disclosure
  7. decide when to use a skill and when to fine-tune

Every tool, but no know-how

After EP13 our agent can reach almost any tool. But give it a real task — “Summarize 3 papers on agent memory for first-year students” — and it has to work out for itself which tools to use, in what order, what the result should look like, and what to check before handing it in. Like an intern on day one with a full toolbox and no one telling them how the job is done. Writing the how-to for every job into the system prompt makes it pages long, and it’s sent on every call. A skill packages the know-how for one job, so the agent can pick it up when it needs it.

What is a skill? Five parts in one module

The book defines a skill as a self-contained capability module that gives an agent expertise in one task (Roitman 2026, sec. 22.1). A skill has five parts:

The idea was popularized by Voyager, a Minecraft agent that built up a library of verified code skills and reused them. And a skill can be loaded, removed or swapped without retraining the model.

The book sums up the three words in one picture: a tool is a hammer · a skill is knowing how to frame a house · an agent is the carpenter who picks which skills to apply.

In Lab 1 the same task runs twice. Without a skill: 621 words of markdown, no citations, the checks fail. With the paper-summary skill: three JSON sentences, every one citing a paper it really opened, every check passes — for input tokens that go from 212 to 463 on every model call.

Three ways to load skills

In Lab 2 a library of six skills: loading them all statically took 4,841 input tokens for one summary; a router choosing from names and descriptions took 2,322, its own call included. A skill described only as “Formats text.” made the router answer none to a citation question; one clearer line of description fixed it. And permissions filtered before the router kept the teacher’s grading skill out of a student’s sight.

In Lab 3 our resolver gives the order paper-summary → citation-format → literature-review, and stops before any model call when meeting-notes is missing, or when citation-format 2.x is required but the library has 1.1.0. literature-review has no tools of its own, yet produces cited paragraphs and an APA reference list from its sub-skills.

Case study: the augmented LLM and the simple loop

The book takes Anthropic’s approach as a case study (Roitman 2026, sec. 22.3): start with the simplest solution; separate workflows, where we lay out the path, from agents, where the model decides (see EP04 and its five patterns, which the book says work as skill templates); and the smallest unit is never a bare model but an augmented LLM = model + retrieval + tools + memory — a skill-equipped model.

The key observation: the most effective agents aren’t the most complex, but simple loops with good tools. The intelligence comes from the model, the quality of the tool descriptions, and the clarity of the task framing — the last two are what skills give structure to.

Five design recommendations: keep the loop simple · invest in tool descriptions · use structured outputs · build in recovery · limit each skill’s scope (a skill that tries to do everything does nothing well).

The skill lifecycle in six stages

Find out which skills exist → select for the request → activate (put instructions, tools and knowledge into the context) → execute → deactivate (remove them to free space) → learn (update examples or routing) (Roitman 2026, sec. 22.4). Like a chef who puts a recipe card on the counter, puts it back when done, and notes “less salt” on it for next time.

In Lab 3 a library that learns, Voyager-style: when no skill fits, the agent writes a code skill with a test, runs the test, and stores it; the next question reuses it. From an empty library we got two skills (papers-per-year-count, sort-papers-by-year), reused twice more. A caution: exec runs code the model wrote — fine only in a lab; a real system needs a sandbox.

Manifests, registries, marketplaces

As skills multiply they need five things (Roitman 2026, sec. 22.5): a manifest (name, capabilities, required tools, input schema) · versions, pinned for reproducible results · dependencies — MCP servers, API keys, other skills · permissions — not every agent should get every skill · a marketplace to publish and install skills, like pip. The book says plainly that no industry-standard manifest schema exists yet — the SKILL.md layout in the labs is one that several tools use.

Skills vs fine-tuning

The two are complementary: fine-tuning gives the base abilities (following instructions, the tool-call format, reasoning), and skills add task-specific expertise on top, at runtime (Roitman 2026, sec. 22.6).

Written ourselves vs deepagents

In Lab 4 the same skills with LangChain’s deepagents: SkillsMiddleware discovers the skills from their folders; there is no separate router — the working model chooses, then opens SKILL.md with read_file. The first call offers only read_file; after the skill is read, search_papers and get_paper appear (progressive disclosure, metadata.include_tools). Permissions come from a different set of sources per role; the teacher opens the rubric and scores 1/3. The trade-off: one summary took 5,937 input tokens, against about 2,300 for our own router, and the resolver and learning library aren’t built in. With create_deep_agent and its many tools, Gemma handed work to a subagent without opening the skill, so we assemble create_agent with just two middlewares.

Lab

Every model output in the videos comes from a real run. The paper records are teaching data (real arXiv ids, titles, authors and years; one-line summaries written for the lab). Your own runs may differ — especially the names and code of the skills the model writes in Lab 3, and runs where a test fails on the first try.

Review questions

  1. How is a skill different from a tool? Name the five parts of a skill you would like to write.
  2. With a library of 200 skills, would you load statically or dynamically — and what would you watch out for?
  3. In Lab 2, why did the router miss with formatter, and what fixed it without touching the router’s code?
  4. Why should a resolver stop before any model call when a version doesn’t match?
  5. In Lab 3, why is the model’s own test only a first check, and what did Voyager check with?
  6. What does progressive disclosure in deepagents buy you, and what does it cost?
  7. What kind of job would you fine-tune for, rather than write a skill?
