Learning objectives

After this episode you will be able to

  1. Explain the textbook’s six agent design principles, with an example of each
  2. Write tool descriptions and error messages a model can use correctly
  3. Tell which failures the harness should handle itself and which need a clear error sent back to the model
  4. Add a trace to an agent loop and build a test suite with diverse inputs, each run several times
  5. Choose a pattern with three questions and Table 19.3, starting at the top row and measuring before you move down
  6. Map each LangChain middleware to the code you wrote yourself

Two teams, one task

Picture two teams with the same task: summarize new papers for a lecturer every morning. The first team chains three LLM steps in a straight line, and it works within a week. The second builds five agents that talk to each other, and a month later they are still debugging — they can’t even tell where it breaks. The second team didn’t write worse code; they chose a structure more complex than the task.

If the patterns from EP04–EP05 are recipes, design principles are what a chef does for every dish, whatever the menu — taste before serving. The textbook distills six principles from Anthropic’s guide to building effective agents (Schluntz and Zhang 2024) and says they apply across all patterns (Roitman 2026, sec. 19.3).

Six design principles

① Keep it simple

Use the simplest architecture that works, and add complexity only when it has been shown to be necessary. To buy snacks at the shop at the end of the street, you walk — you don’t call a ten-wheel truck.

Translating an abstract into Thai and summarizing it in three lines needs a two-step prompt chain (translate → summarize), not a manager, a translator and a reviewer. The textbook says it plainly: a prompt chain that solves the problem is always preferable to a multi-agent system that might. Every layer you add means more LLM calls, more waiting, and one more place to break.

② Transparency over cleverness

Every step of an agent should be inspectable — no hidden state, no reasoning you can’t see. Think of a maths exam: if you only write the answer and it’s wrong, the teacher can’t tell where you went wrong; if you show your working, they can point to line three.

For an agent, the working is the trace. Say the research agent answers that there is no research on a topic, which isn’t true. Open the trace and you see that in step two it searched with year_from=2030. The textbook says opaque architectures make debugging impossible.

In Lab 2: we add a trace to the agent loop and ask for papers “from the last two years”. The answer looks right, but the trace shows the model searched with a year that was too old, because it didn’t know today’s date. The fix is to put the date in the system prompt.

③ Provide good tools

The model never sees a tool’s code; it only sees the name, the description, and the argument types. It’s like a toolbox with no labels — no wonder it picks the wrong one.

The textbook says a tool with a vague description will be misused, while one with a precise schema will be selected correctly, and calls good tools force multipliers: the same model does much better with them.

In Lab 1: with an argument named n, the model sent n=10 every round (and got 5 papers older than 2023 every time). Renamed to year_from with a clear description, it sent year_from=2023 correctly in all 5 rounds.

④ Plan for failure

Every tool call can fail: an API times out, or the provider says you’re calling too often (429). The textbook says to build retry logic, fallbacks and graceful degradation at the harness level, so the model doesn’t need to reason about infrastructure failures.

Retrying is like calling a friend whose line is busy: you wait a moment and call again rather than redialing over and over. If every route is closed, the system still shouldn’t fall over: it answers from old data in a cache and says honestly that it may be out of date. That is graceful degradation.

NotePrinciples ③ and ④ work together

When the infrastructure fails, the harness handles it quietly. When the model uses a tool wrongly, send a clear error back so the model can fix it.

In Lab 1: the harness retries after 1 second, then 2 seconds. When every route is closed it answers from the library copy, but the model dropped the “may be out of date” note every time we tested, so the harness attaches the warning itself.

⑤ Use structured outputs

Use a JSON schema or function calling to constrain the answer’s format. An agent that answers in free-form text you have to pick apart with regex is fragile; one that answers in validated JSON is robust. It’s a form with boxes to fill in, versus a letter that can say anything. We did this hands-on in EP02.

⑥ Test with diverse inputs

Agent behaviour is more variable than single-turn chat: the same prompt, run twice, can call tools in a different order. So the textbook recommends testing adversarially — with edge cases, ambiguous requests and malformed inputs. It’s like testing a calculator: you don’t just press 2 + 2; you try dividing by zero.

In Lab 2: a suite of 7 cases, 3 rounds each, finds a bug we hadn’t thought of: the topic that isn’t in the library failed every round, and the trace showed the cause was our own search, not the model (find_papers counts a match if a single word of the title matches, so “learning” pulled in Chronos). After the fix: 21/21.

Choosing a pattern: three questions

The textbook says the choice depends on three things (Roitman 2026, sec. 19.4):

  1. How predictable is the task’s structure? Do you know the steps in advance?
  2. How many LLM calls can you afford? Both in how long the user waits and in cost.
  3. Does quality require iteration?

Table 19.3: the decision matrix

The textbook puts every pattern in one table that works as a decision matrix. These nine rows are everything from EP04 and EP05 (except multi-agent, which comes in a later episode).

To use it, start at the top row and move down only when the simpler pattern demonstrably fails. Say the task is to find five papers and summarize them: try a chain first, and if it fails because you can’t know how many searches it takes, move down to ReAct.

In Lab 3: we build a meter for LLM calls and cost, then try prompt chaining (top row) and ReAct (middle row) on two tasks.

  • Task A, summarize PatchTST in three points: the chain is right every round with 2 LLM calls; ReAct is right too but uses 3 calls and costs about 3× as much, so we stop at the top row.
  • Task B, papers from 2023 on that learners rated ≥ 4.5: the chain is wrong every round, and silently, because it reads only the first result; ReAct is right every round, so we move down a row.

The chain’s first step uses structured output (principle ⑤).

ImportantPatterns compose, but know when to stop

One planning agent may use chaining for each step, an evaluator-optimizer for review, and routing to dispatch subtasks. But the textbook ends with this: the art is knowing when to stop adding layers.

Hand-written vs framework

In Lab 4 we apply every principle again with LangChain (langchain==1.4.7). Each piece maps to code from Labs 1–3.

The code gets much shorter, but the framework doesn’t decide for us which errors to retry, how to order the middleware, or what the user must see. Those decisions still belong to the designer.

Review questions

  1. Why is a prompt chain that solves the problem better than a multi-agent system that might?
  2. The agent says there is no research on a topic when there is. How would you use the trace to find out why?
  3. In Table 6.1, how does the error message on the right help the model?
  4. How should an API timeout be handled differently from the model sending a wrong argument?
  5. Why run each input in a test suite several times?
  6. In Lab 3, why does Task A stop at prompt chaining while Task B moves down to ReAct?
  7. Which LangChain middleware replaces the retry loop we wrote ourselves in Lab 1?
