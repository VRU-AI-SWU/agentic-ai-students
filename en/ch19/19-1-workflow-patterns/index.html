Learning objectives

After this module you will be able to

  1. Explain how a workflow differs from an agent, and say when a workflow is enough
  2. Design a prompt chain with validation gates between steps
  3. Build a router that classifies once, then hands off to a specialist handler
  4. Call an LLM in parallel with sectioning and voting, and merge the results in code
  5. Explain how orchestrator-workers differs from parallelization
  6. Build an evaluator-optimizer loop with a threshold and a retry budget

Workflow or agent

The first thing chapter 19 stresses is that not every task needs an agent (Roitman 2026, sec. 19.1; Schluntz and Zhang 2024). In a workflow, the system fixes the order of steps in advance and calls the LLM at set steps — like a train on rails. In an agent, the LLM decides what to do next — like handing it the steering wheel.

ImportantAlways start with a workflow

Move to an agent only when the task genuinely needs dynamic routing or open-ended exploration. The running example in this module is the Cogito Learn teaching assistant: we already know student questions come in only a few kinds, so a workflow is enough.

1. Prompt Chaining

Split a big task into a fixed sequence of LLM calls; the output of one step is the context of the next. Between steps, validation gates catch errors early — like quality checks between stations on a factory conveyor belt. A gate can be an LLM or plain code.

Each step can use a different prompt, model or temperature, and every intermediate result can be inspected. It fits tasks that are already a sequence of steps: content generation, data transformation, multi-stage analysis.

In Lab 1: the abstract passes every gate, an exam-room notice is stopped at the first gate, and when the summary is limited to two lines, the code gate stops it midway.

2. Routing

A classifier (an LLM or a traditional model) looks at the input first, then sends it to a specialist handler — like hospital triage: one check, then the right department.

Routing fits when there are clearly distinct kinds of input and each needs a different prompt, tool or model. The textbook’s examples are customer-support triage and multi-modal input handling.

In Lab 2: all six questions land in the right place, including a trick question that contains the word “error” but is really a concept question.

3. Parallelization

Call the LLM several times at once and let our code merge the results. The textbook describes two kinds:

  • Sectioning (fan-out): split the work into independent parts — e.g. review code for security, performance and style at the same time — then merge, deduplicate and rank by severity. Like three teachers each marking a different section of an exam at the same time.
  • Voting: send the same prompt N times with different seeds or temperatures, then pick an answer by majority vote, a reward model, or an LLM judge.

If the calls take \(t_1, \dots, t_n\), the parallel run takes about as long as the slowest call, not the sum:

\[ T_\text{sequential} = \sum_{i=1}^{n} t_i, \qquad T_\text{parallel} \approx \max_i t_i \tag{4.1}\]

In Lab 3: three reviews one at a time took 3.9 s; all at once took 1.6 s, as Equation 4.1 predicts. Voting five times gave “low” four times. (Your numbers will vary with server speed.)

4. Orchestrator-Workers

Now the LLM decides how to split the work. The orchestrator analyses the task and writes a plan of subtasks; workers, which may use different prompts or tools, do each subtask; a synthesizer merges the results into one answer — like a head chef who reads the order before deciding how to split the work among the cooks.

Unlike parallelization, the split is not hard-coded. The textbook recommends it for open-ended tasks where the number and kind of subtasks can’t be known in advance, such as “refactor this codebase”.

In Lab 4: the exact same code, two goals, two different plans — the first goal got four subtasks; the question about AI hints got two, and paper P2 wasn’t used at all.

5. Evaluator-Optimizer

A feedback loop between two models: a generator produces work, an evaluator scores it against explicit criteria. Below the threshold, the evaluator’s critique is appended to the generator’s context and it tries again — until the work passes or the retry budget runs out. Like a writer and an editor.

It fits tasks with clear quality criteria — code that must pass tests, writing that must follow a style guide, translation that must keep the meaning — and it improves results without training the model.

In Lab 5: the first draft scored 6/10 because technical terms were translated into Thai; after the critique went into the context, round two scored 10/10 — even though the generator never saw the glossary.

The five patterns side by side

All five run the LLM on a path the system defines, so they stay predictable, testable and affordable — and they compose: a router can hand off to a chain, or one step of a chain can be an evaluator-optimizer. The last two already give the model more say, which is the bridge to autonomous agents in EP05.
