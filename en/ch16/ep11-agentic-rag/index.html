Learning objectives

By the end of this episode you will be able to

  1. transform a question before searching (HyDE, step-back, multi-query, RAG-Fusion) and explain why it helps
  2. explain why a cross-encoder re-ranks retrieved chunks but can’t do the first search
  3. describe how Self-RAG, CRAG, Adaptive RAG and Graph RAG each change the RAG pipeline
  4. name the questions static RAG fails on, and describe agentic RAG as a sequence of decisions
  5. build a router and a plan → retrieve → evaluate → generate loop with an iteration limit, by hand and with LangGraph
  6. measure retrieval with Recall@K, MRR and NDCG, and answers with faithfulness and answer relevance, and say what each one misses
  7. name the six failure modes of RAG in the textbook

The question we still can’t find

In EP10, one question missed with every method: which analogy does the RAG chapter of Roitman’s The Hitchhiker’s Guide to Agentic AI use to explain RAG? With the author’s name and the book’s title in it, the library-card chunk sat at rank 8 with dense search, 5 with hybrid and 17 with parent-child. This episode tries two things: transform the question before searching, and let an agent decide what to search, where, and whether it has found enough. Then the key question: how do we measure whether RAG really got better?

Before retrieval: transform the question

User questions are often ambiguous, too short, or worded differently from the documents (Roitman 2026, sec. 16.5.1).

  • HyDE: have the model write a hypothetical answer, and embed that instead of the question. The draft may be wrong: we only search with it, we don’t answer with it. Written like the documents, it lands closer to the right chunk (Equation 16.20).
  • Step-back: ask a broader question first. For the boiling point of ethanol at 2 atm, also search what affects the boiling point of liquids.
  • Multi-query: rewrite the question several ways, search for each, merge the results.
  • RAG-Fusion: multi-query plus the original, all ranked lists merged with RRF (Listing 16.8), the formula from EP10 Lab 2. A chunk that ranks well for many queries rises to the top.

In Lab 1 HyDE’s draft said the book uses an “open-book exam”, which is wrong, yet searching with it put the library-card chunk at rank 1. Plain multi-query kept the book’s title in every variant (ranks 12, 13 and 9; fused: 9); told to leave out titles and author names, the fused result was rank 1.

After retrieval: re-rank and compress

The retriever from EP10 encodes questions and documents separately, so document embeddings are computed ahead of time and search is fast. A cross-encoder reads the question and a document together in one pass: much more accurate, but slow, and it can’t do the first search because there is nothing to store in advance. So it re-ranks only the chunks already retrieved, typically 20 to 100 (Roitman 2026, sec. 16.5.2). Like hiring: screen résumés by keyword first, then interview five people. Contextual compression then cuts each chunk down to the part that answers the question.

In Lab 1 the cross-encoder put the library-card chunk at rank 1 with a score of 0.996; the next chunk scored 0.50. On 20 test questions, hit@3: dense 12 · HyDE 16 · RAG-Fusion 14 · re-rank 18 · HyDE + re-rank 19.

RAG that checks itself, and two more patterns

  • Self-RAG trains one model to decide whether to retrieve, whether what it got is relevant, whether its answer is supported and whether it is useful, through four special tokens learned in training.
  • CRAG keeps the model and adds an evaluator that grades each document correct, ambiguous or incorrect: some correct → strip the irrelevant sentences and answer from the rest; all incorrect or ambiguous → fall back to web search.
  • Adaptive RAG sorts questions by difficulty with a small classifier: no retrieval, one retrieval, or several rounds.
  • Graph RAG extracts entities and relations into a graph, finds communities and summarizes each. It excels at global questions (the main themes of a corpus) but is expensive to build; for local questions standard RAG is still better.

Agentic RAG

Static RAG retrieves once, then answers. The textbook lists where it fails: multi-hop questions (“who founded the company that acquired OpenAI’s main competitor in 2023?”), ambiguous questions, sub-questions that need different knowledge bases, and a first search that shows a different query is needed (Roitman 2026, sec. 16.7). Agentic RAG treats retrieval as a sequence of decisions: the state is the question and the documents found so far; the actions are retrieve, reason, generate or stop; the reward is a correct answer. Like ReAct in EP05, with search as the main tool.

Routing across sources

The book also advises a fallback source, searching several sources and fusing them with RRF, and logging every routing decision with its reason.

The loop

The iteration counter stops the agent from searching forever, like the LoopGuard in EP08. The book builds this loop in LangGraph (Listing 16.10).

In Lab 2 we built it in plain Python with three sources: BM25, embeddings, and the book’s table of contents. A two-part question took 11 model calls; “What does PLAID stand for?”, which the book never says, ran 3 rounds and answered that the context does not contain it. The long question: the table of contents missed, the grader rejected it, and round 2 tried the vector store and found the library card. Our CRAG-style grader had graded all three embedding top-3 chunks for it incorrect.

In Lab 4 the same agent in LangGraph took the same paths. Written as in the book, nodes that return {**state, ...} make the operator.add reducer add the documents again: 4 documents [301, 357, 301, 357] instead of 2. Return only the keys that changed. With the cap set too high, recursion_limit stopped the graph with GraphRecursionError.

Search-R1

Everything above is steered by the prompt. Search-R1 trains the model with reinforcement learning to decide when to search, what for and how many times, rewarded for a correct final answer (Table 16.4). The book reports a 7B model about 15–20% more accurate than single-retrieval RAG. This series doesn’t train models, so we use prompt-based agentic RAG.

Beyond the textbook: walk the table of contents

This part is not in the textbook.

To find the library card in a 600-page book you don’t compare every page: you open the table of contents, pick a chapter and a section, and go back if it’s wrong. MemWalker (Chen et al. 2023) builds a tree of summaries and has the model walk it from the top: at each node, open a child, go back up, or answer. RAPTOR (Sarthi et al. 2024) also builds a summary tree but searches it with embeddings; the open-source PageIndex walks a table-of-contents tree with no embeddings. MemWalker reports this needs a large model (around 70B).

In Lab 2 Gemma 4 26B walked the book’s 157-entry table of contents from the root to Framework Comparison (pp. 359–360) in 3 steps, with no embeddings.

Evaluating RAG

Errors can start at any stage and compound, so the textbook measures three levels: retrieval, generation and end to end, and warns against optimizing only one: a large K gives high recall but fills the context with barely relevant chunks (Roitman 2026, sec. 16.8).

  • Recall@K: the share of the right chunks that are in the top K (Equation 16.22).
  • MRR: the mean of 1 / rank of the first right chunk (Equation 16.24). Ranks 1, 3 and a miss: (1 + 1/3 + 0) / 3 ≈ 0.44.
  • NDCG@K: right chunks near the top count more (Equation 16.25).
  • Faithfulness: supported claims ÷ all claims, with an LLM as the judge (Equation 16.26). Three claims, two supported: 2/3.
  • Answer relevance: generate questions back from the answer and compare them with the original (Equation 16.27).

Re-ranking lifts MRR from about 0.5 to about 0.8 but hardly moves recall: it re-orders the same twenty chunks rather than finding new ones.

In Lab 3 the wrong no-RAG answer still scored 0.78: its central claim was judged unsupported, but every general claim weighs the same. Answer relevance couldn’t tell the three apart. Only correctness against a reference answer, written by a person, separated them, and it marked the re-ranked answer right.

Six failure modes, and production

  1. Retrieval miss: the document is in the library but isn’t retrieved (our long question).
  2. Context poisoning: wrong or contradictory documents pull the answer wrong.
  3. Lost in the middle: models attend to the start and end of a long context more than the middle.
  4. Over-retrieval: too many chunks dilute the relevant ones, and cost more.
  5. Hallucination despite retrieval: the model ignores the documents.
  6. Citation fabrication: citing a document that doesn’t say that.

For production, the textbook calls the embedding model the most impactful choice, since it sets the ceiling for retrieval. It also compares vector databases, lists ways to cut latency (filter by metadata first, query sources in parallel), and recommends updating a changed document’s chunks with a version number instead of rebuilding the index (Roitman 2026, sec. 16.9).
