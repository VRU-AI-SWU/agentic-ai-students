  2. Explain how a model acts through tools even though it can only write text

A request a chatbot can’t handle

Suppose a student types: “How many days until the midterm? Please book a tutoring room for me.” Even a very capable chatbot can usually only say: sorry, I don’t know today’s date, and I can’t book rooms — and then it stops and waits. Another kind of assistant opens the calendar itself, checks which rooms are free, asks us first whether it may book this one, and then actually books it. Both can use the very same model. What differs is what we build around the model.

Chatbot: answer once, then wait

The book calls what we use every day the single-turn chatbot: the model gets one message, produces one response, and waits (Roitman 2026, ch. 15). It’s like an older student you can phone for advice: they can tell you what to do and which website to visit, but they can’t do it for you. And what they know is only what they learned in training — from EP01 we know the model doesn’t know today’s date and has never seen our course’s exam calendar.

In Lab 1: calling Gemma once with this request, the model says itself that it doesn’t know our exam date and can’t access the booking system.

Agent: an LLM working in a loop

The book defines an agentic AI system as one where an LLM works in a loop: it takes in what it sees from its environment, reasons about what to do next, and acts — looping until it reaches the goal, or until it stops to ask a person (Roitman 2026, ch. 15). What it sees each round is an observation: a user message, a tool result, or sensor data. An action can be a tool call, running code, or an API request. This idea of a model alternating between reasoning and acting is ReAct, which comes back in EP05 (Yao et al. 2023).

Think of an assistant asked to arrange a tutoring room:

Each round’s next step comes from what it just saw in the previous round. That is exactly what a single model call can’t do.

Tools: the model asks, the program acts

A model can only write text; it can’t press the booking button itself. The answer is tools: functions in our own program, such as opening the calendar, finding free rooms and booking a room. We tell the model which tools it has. When it wants one, it writes a request as a form, called a tool call, saying which tool and with which values (Schick et al. 2023). Our program then actually calls that function, and the result goes back as the next round’s observation. It’s like a doctor who writes a prescription while the pharmacist hands out the medicine.

{"name": "find_rooms", "arguments": {"date": "2026-11-12"}}

In Lab 1, the “pharmacist” is these three lines:

def run_tool(call):
    args = json.loads(call.function.arguments or "{}")
    return json.dumps(FUNCS[call.function.name](**args), ensure_ascii=False)

Harness: the car around the engine

Who runs the loop, who calls the tools, who keeps track of what’s been done? The book calls this the harness, and compares it to an operating system for agents: it runs the agent’s loop, manages the context-window budget, dispatches tools, recovers from errors, keeps state, and logs what the agent did so we can look back (Roitman 2026, ch. 15). If the model is the engine, the harness is the whole car — steering wheel, brakes and seat belts. However powerful the engine, it takes us nowhere without the car.

Our first harness, in Lab 1, is this loop:

def run_agent(history, max_steps=MAX_STEPS):
    for step in range(1, max_steps + 1):
        msg = call_llm(history)
        if not msg.tool_calls:                      # no more tool requests = finished
            history.append({"role": "assistant", "content": msg.content})
            return msg.content
        history.append({"role": "assistant", "content": msg.content or "",
                        "tool_calls": [c.model_dump() for c in msg.tool_calls]})
        for call in msg.tool_calls:
            if call.function.name in NEEDS_APPROVAL:  # important action: park it for a person
                PENDING.append(call)
                continue
            result = run_tool(call)
            history.append({"role": "tool", "tool_call_id": call.id, "content": result})
        if PENDING:
            return "⏸ awaiting approval"
    return f"⚠️ stopped: reached {max_steps} steps"

In Lab 1: with three tools and this loop, the agent calls get_calendar, sees today is Tuesday the 10th, works out that this Thursday is the 12th, and calls find_rooms. Finally it says the exam is eight days away, and since Room 3 is free at both 1 pm and 3 pm, it doesn’t guess — it asks us.

The five challenges of agents

Moving from chatbot to agent, the book says we meet five basic challenges that a single model call can’t solve (Roitman 2026, ch. 15).

Persistence matters because the model itself remembers nothing between calls; each time, it sees only what is in its context window. Remembering is the harness’s job: it keeps the history and sends it back every time — like an assistant who loses their memory every morning but keeps a notebook. For action, the book compares a standard way of connecting tools to a USB port: one plug that works with every device. That’s MCP, in EP13.

In Lab 1: replying “13:00” in the same history, the agent correctly books Room 3 on the 12th at 1 pm. But with a fresh history, asking to move to 3 pm, it asks which day and which room. An agent’s memory isn’t in the model; it’s in the history the harness keeps.

Safety: guardrails and human-in-the-loop

The last challenge matters most once an agent can really act. The book says autonomous action needs three things: guardrails, rules the harness enforces, such as booking only tutoring rooms and looping at most eight times; human oversight, or human-in-the-loop, like an intern who needs a manager’s signature before paying anything; and, when uncertain, backing off gracefully — saying so or asking a person is better than claiming a booking that never happened.

In Lab 1 there are three layers of guardrails:

  • Step limit: with max_steps=1, the agent calls the calendar once and stops: “reached 1 step”
  • A check inside the tool: book_room first checks the room is really free at that time, and returns an error instead of booking blindly
  • Approval: with book_room in NEEDS_APPROVAL, asking to move to 3 pm parks the request; the booking stays at 1 pm until we approve, then changes to 3 pm

The Agentic AI stack: a map of the series

The book doesn’t see an agent as a single model but as a system of layers, each solving one problem (Roitman 2026, fig. 15.1). This picture is also the map of our series, and every layer is added to one project as we go: a Research Assistant Agent.

In the middle is the agent core, surrounded by the harness, which decides when to look things up, when to call a tool, when to hand work to another agent, and when to ask a person. Below are what the agent connects to; above is the user, who sets goals, gives feedback and supervises. Design patterns (EP04–06), evaluation (EP17–18) and frameworks (EP19) each get their own episodes. The book sums it up: agentic AI is not just prompting — it takes careful engineering of context management, error handling, safety guardrails and observability at every layer.

Write it yourself vs a framework

Lab 2 builds the same assistant again with LangChain and compares it piece by piece. The book compares frameworks in Chapter 18 (Roitman 2026, Table 18.1); the table below is what we actually saw in the two labs.

safe = create_agent(llm, tools=TOOLS, system_prompt=SYSTEM, checkpointer=memory,
                    middleware=[HumanInTheLoopMiddleware(interrupt_on={"book_room": True})])
config = {"configurable": {"thread_id": "student-1"}}
safe.invoke({"messages": [{"role": "user", "content": "Can we move it to 3 pm?"}]}, config)  # ⏸ parked
safe.invoke(Command(resume={"decisions": [{"type": "approve"}]}), config)                 # ✅ booked

In Lab 2: the agent takes exactly the same steps as in Lab 1, and keeps the same kind of history inside (human, ai, tool, ai, tool, ai). But the framework doesn’t remember by itself: with no checkpointer, replying “13:00” books nothing. With a checkpointer it books in thread student-1, while thread student-2 asks which day and which room. ModelCallLimitMiddleware(run_limit=1) stops after one calendar call, and HumanInTheLoopMiddleware holds book_room: the booking stays at 1 pm until we send back "approve", then changes to 3 pm.

A framework makes the code shorter and comes with ready-made extras, such as saving history to a database or rejecting with a reason. But every piece is something we wrote ourselves in Lab 1, and when an agent behaves strangely, what we learned in Lab 1 tells us where to look.

Let the model think, let the tools act, and let people decide what matters.

Review questions

  1. How does a single-turn chatbot differ from an agent? Use the tutoring-room request as an example.
  2. A model can only write text — so how does an agent book a room? Who actually runs the function?
  3. What does a harness do, and which part of the Lab 1 code is our harness?
  4. Why did the agent in Lab 1 ask us back instead of booking a room right away?
  5. With a fresh history, what did the agent do when asked to move the booking, and what does that say about an agent’s memory?
  6. What are the three layers of guardrails in Lab 1, and where is each in the code?
  7. In Lab 2, why was nothing booked before we added a checkpointer?
  8. Why does the check that a room is really free stay inside book_room, even with LangChain?
