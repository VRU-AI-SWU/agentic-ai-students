EP04 Workflow Patterns

วัตถุประสงค์การเรียนรู้

เมื่อจบ module นี้ ผู้เรียนจะสามารถ

  1. อธิบายความแตกต่างระหว่าง workflow และ agent และบอกได้ว่าเมื่อไร workflow ก็เพียงพอ
  2. ออกแบบ prompt chain ที่มี validation gate ระหว่างขั้น
  3. สร้าง router ที่ classify ครั้งเดียวแล้วส่งงานต่อให้ handler เฉพาะทาง
  4. เรียก LLM พร้อมกันแบบ sectioning และ voting แล้วรวมผลด้วยโค้ด
  5. อธิบายว่า orchestrator-workers ต่างจาก parallelization อย่างไร
  6. สร้าง evaluator-optimizer loop ที่มี threshold และ retry budget

Workflow หรือ agent

ตำราย้ำเป็นเรื่องแรกของบทที่ 19 ว่า ไม่ใช่ทุกงานที่ต้องใช้ agent (Roitman 2026, หมวด 19.1) ใน workflow ระบบเป็นผู้กำหนดลำดับขั้นตอนไว้ล่วงหน้า แล้วเรียก LLM ในขั้นที่กำหนด เหมือนรถไฟที่วิ่งตามราง ส่วน agent ให้ LLM ตัดสินใจเองว่าจะทำอะไรต่อ เหมือนยกพวงมาลัยให้มันขับ

สำคัญเริ่มจาก workflow ก่อนเสมอ

ขยับไปใช้ agent เมื่องานต้องการเส้นทางแบบ dynamic หรือการสำรวจแบบเปิดจริงๆ เท่านั้น ตัวอย่างตลอด module นี้คือ ผู้ช่วยอาจารย์ของ Cogito Learn ซึ่งเรารู้อยู่แล้วว่าคำถามมีไม่กี่ประเภท workflow จึงเพียงพอ

1. Prompt Chaining

แบ่งงานใหญ่เป็นลำดับ LLM call ที่ตายตัว ผลลัพธ์ของขั้นหนึ่งเป็น context ของขั้นถัดไป และระหว่างขั้นมี validation gate คอยจับข้อผิดพลาดตั้งแต่เนิ่นๆ เหมือนจุดตรวจคุณภาพบนสายพานโรงงาน gate จะใช้ LLM ตรวจ หรือเขียนโค้ดตรวจธรรมดาก็ได้

ข้อดีคือแต่ละขั้นใช้ prompt, model หรือ temperature ต่างกันได้ และเปิดดูผลระหว่างทางได้ทุกขั้น เหมาะกับงานที่เป็นลำดับขั้นอยู่แล้ว เช่น สร้างเนื้อหา แปลงข้อมูล หรือวิเคราะห์หลายขั้น

ใน Lab 1: abstract ผ่านครบทุกด่าน ประกาศห้องสอบถูก gate แรกหยุดไว้ และเมื่อตั้งให้สรุปได้แค่สองบรรทัด gate ที่เป็นโค้ดก็หยุดผลลัพธ์ไว้กลางทาง

2. Routing

Classifier (LLM หรือ model แบบดั้งเดิม) ดู input ก่อน แล้วส่งไปยัง handler เฉพาะทาง เหมือนจุดคัดกรองในโรงพยาบาลที่ถามอาการครั้งเดียวแล้วส่งไปแผนกที่ถูก

Routing เหมาะเมื่องานมีหลายประเภทที่ชัดเจน และแต่ละประเภทต้องการ prompt, tool หรือ model ต่างกัน ตัวอย่างในตำราคือการคัดกรองงาน customer support และการรับ input หลายรูปแบบ

ใน Lab 2: คำถามทั้งหกข้อไปถูกที่ รวมถึงข้อหลอกที่มีคำว่า error แต่จริงๆ เป็นคำถามแนวคิด

3. Parallelization

เรียก LLM หลายครั้งพร้อมกัน แล้วให้โค้ดของเรารวมผล ตำราแบ่งเป็นสองแบบ

  • Sectioning (fan-out) แบ่งงานเป็นส่วนที่ไม่ทับกัน เช่น review โค้ดสามด้าน security / performance / style พร้อมกัน แล้วรวมผล ตัดซ้ำ และเรียงตามความรุนแรง เหมือนครูสามคนตรวจข้อสอบคนละตอนในเวลาเดียวกัน
  • Voting ส่ง prompt เดียวกัน N ครั้งด้วย seed หรือ temperature ต่างกัน แล้วเลือกคำตอบด้วยเสียงข้างมาก, reward model หรือ LLM-as-judge

ถ้า call แต่ละครั้งใช้เวลา \(t_1, \dots, t_n\) เวลารวมของแบบพร้อมกันใกล้กับ call ที่ช้าที่สุด ไม่ใช่ผลรวม

\[ T_\text{sequential} = \sum_{i=1}^{n} t_i, \qquad T_\text{parallel} \approx \max_i t_i \tag{1.1}\]

ใน Lab 3: review สามด้านทีละ call ใช้ 3.9 วินาที แบบพร้อมกันใช้ 1.6 วินาที ตาม สมการ 1.1 ส่วน voting ห้าครั้งได้ “low” สี่เสียง (ตัวเลขของคุณจะต่างไปตามความเร็วของ server)

4. Orchestrator-Workers

คราวนี้ LLM เป็นผู้ตัดสินใจว่าจะแบ่งงานอย่างไร orchestrator วิเคราะห์โจทย์ สร้างแผนเป็นงานย่อย ส่งให้ worker ที่อาจใช้ prompt หรือ tool ต่างกัน แล้ว synthesizer รวมผลเป็นคำตอบเดียว เหมือนหัวหน้าเชฟที่ต้องดูออร์เดอร์ก่อนถึงจะรู้ว่าต้องแบ่งงานให้ลูกมือกี่คน

ความต่างจาก parallelization คือวิธีแบ่งงานไม่ได้ตายตัวในโค้ด ตำราบอกว่าเหมาะกับงานปลายเปิดที่ไม่รู้ล่วงหน้าว่าจะมีงานย่อยกี่ชิ้น เช่น “refactor this codebase”

ใน Lab 4: โค้ดเดียวกันทุกบรรทัด แต่สอง goal ได้แผนต่างกัน goal แรกได้สี่งานย่อย ส่วนคำถามเรื่อง AI hints ได้สองงานย่อยและไม่ใช้ paper P2 เลย

5. Evaluator-Optimizer

Feedback loop ของสอง model: generator สร้างผลงาน evaluator ให้คะแนนตามเกณฑ์ที่เขียนไว้ชัดเจน ถ้ายังไม่ถึง threshold คำวิจารณ์ (critique) จะถูกต่อเข้า context ของ generator แล้ววนใหม่ จนผ่านหรือจน retry budget หมด เหมือนนักเขียนกับบรรณาธิการ

เหมาะกับงานที่มีเกณฑ์คุณภาพชัดเจน เช่น โค้ดที่ต้องผ่าน test งานเขียนที่ต้องตรง style guide หรืองานแปลที่ต้องรักษาความหมาย และทั้งหมดนี้ทำได้ โดยไม่ต้อง train model

ใน Lab 5: ร่างแรกได้ 6/10 เพราะแปลศัพท์เทคนิคเป็นภาษาไทย พอต่อ critique เข้าไป รอบที่สองได้ 10/10 ทั้งที่ generator ไม่เคยเห็น glossary

ห้า pattern เทียบกัน

ทั้งห้าแบบใช้ LLM บนเส้นทางที่ระบบกำหนดไว้ จึงคาดเดาได้ ทดสอบได้ และคุมต้นทุนได้ และประกอบกันได้ เช่น router ส่งงานต่อให้ chain หรือขั้นหนึ่งของ chain เป็น evaluator-optimizer สองแบบหลังเริ่มให้ model มีส่วนตัดสินใจมากขึ้น ซึ่งเป็นสะพานไปสู่ autonomous agent ใน EP05

ข้อมูลในโค้ด (abstract, คำถาม, โค้ดที่ตรวจ) เป็นข้อมูลจำลองเพื่อการสอน ส่วน output ของ model ในวิดีโอมาจากการรันจริง

คำถามทบทวน

  1. ทำไมผู้ช่วยอาจารย์ที่ตอบคำถามนักศึกษาจึงใช้ workflow ก็พอ ไม่ต้องใช้ agent
  2. ใน รูปที่ 1.1 ถ้าไม่มี gate หลังขั้น 1 ข้อผิดพลาดแบบไหนจะไหลไปถึงสรุป
  3. ทำไม classifier ใน รูปที่ 1.2 จึงตอบเป็น enum ด้วย temperature 0
  4. จาก สมการ 1.1 ถ้าเพิ่มผู้ตรวจด้านที่สี่ เวลาแบบพร้อมกันจะเปลี่ยนไปอย่างไร
  5. Orchestrator-workers ต่างจาก sectioning ตรงไหน
  6. ถ้าตั้ง threshold เป็น 10 และ budget เป็น 1 ใน รูปที่ 1.4 จะเกิดอะไรขึ้น
