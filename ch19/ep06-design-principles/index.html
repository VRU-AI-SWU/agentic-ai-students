EP06 Design Principles and Choosing a Pattern

§19.3–19.4 · หลักออกแบบ 6 ข้อ · ตาราง 19.3 · trace · ชุดทดสอบ · LangChain middleware

วัตถุประสงค์การเรียนรู้

เมื่อจบตอนนี้ ผู้เรียนจะสามารถ

  1. อธิบายหลักออกแบบ agent 6 ข้อจากตำรา พร้อมยกตัวอย่างของแต่ละข้อได้
  2. เขียน tool description และ error message ที่ model ใช้ได้ถูก
  3. แยกได้ว่าความล้มเหลวแบบไหน harness ควรจัดการเอง และแบบไหนต้องส่ง error กลับให้ model แก้
  4. ใส่ trace ใน agent loop และสร้างชุดทดสอบที่มี input หลายแบบ รันซ้ำหลายรอบ
  5. ใช้สามคำถามและตาราง 19.3 เลือก pattern โดยเริ่มจากแถวบนสุด และวัดผลก่อนขยับลง
  6. บอกได้ว่า middleware แต่ละตัวของ LangChain ตรงกับโค้ดส่วนไหนที่เราเขียนเอง

สองทีม โจทย์เดียวกัน

ลองนึกภาพสองทีมที่ได้โจทย์เดียวกัน คือสรุป paper ใหม่ให้อาจารย์ทุกเช้า ทีมแรกต่อ LLM สามขั้นเป็นเส้นตรง ใช้งานได้ในหนึ่งสัปดาห์ ทีมที่สองสร้าง agent ห้าตัวคุยกัน ผ่านไปหนึ่งเดือนยังแก้บั๊กไม่จบ และไม่รู้ด้วยซ้ำว่าพังตรงไหน ทีมที่สองไม่ได้เขียนโค้ดแย่กว่า แต่เลือกโครงสร้างที่ซับซ้อนเกินโจทย์

ถ้า pattern ที่เราเรียนใน EP04–EP05 คือสูตรอาหาร หลักออกแบบ ก็คือสิ่งที่เชฟทำทุกจานไม่ว่าเมนูไหน เช่น ชิมก่อนเสิร์ฟ ตำรากลั่นหลัก 6 ข้อมาจากแนวทางของ Anthropic (Schluntz และ Zhang 2024) และบอกว่าใช้ได้กับทุก pattern (Roitman 2026, หมวด 19.3)

หลักออกแบบ 6 ข้อ

① Keep it simple

ใช้โครงสร้างที่ง่ายที่สุดที่ทำงานได้ แล้วค่อยเพิ่มความซับซ้อนเมื่อพิสูจน์แล้วว่าจำเป็นจริงๆ เหมือนไปซื้อขนมที่ร้านปากซอย เดินไปก็พอ ไม่ต้องเรียกรถบรรทุก

งานแปล abstract เป็นไทยแล้วสรุปสามบรรทัด ใช้ prompt chain สองขั้น (แปล → สรุป) ก็จบ ไม่ต้องมี agent หัวหน้า นักแปล และผู้ตรวจ ตำราเขียนไว้ชัดว่า prompt chain ที่แก้ปัญหาได้จริง ดีกว่า multi-agent system ที่อาจจะแก้ได้ เพราะทุกชั้นที่เพิ่มคือ LLM call ที่เพิ่มขึ้น เวลารอที่นานขึ้น และจุดที่พังได้อีกหนึ่งจุด

② Transparency over cleverness

ทุกขั้นของ agent ต้องเปิดดูได้ ไม่มี state ที่ซ่อนอยู่ ไม่มีเหตุผลที่มองไม่เห็น เหมือนข้อสอบคณิต ถ้าเขียนแค่คำตอบแล้วผิด ครูไม่รู้ว่าผิดตรงไหน แต่ถ้าแสดงวิธีทำ ครูชี้ได้เลยว่าผิดบรรทัดที่สาม

ใน agent สิ่งที่ทำหน้าที่เป็นวิธีทำคือ trace สมมติ research agent ตอบว่า “ยังไม่มีงานวิจัยเรื่องนี้” ซึ่งไม่จริง เปิด trace ก็เห็นว่าขั้นที่สองมันค้นด้วย year_from=2030 ตำราบอกว่าระบบที่มองข้างในไม่ได้ ทำให้ debug เป็นไปไม่ได้

ใน Lab 2: เราใส่ trace ใน agent loop แล้วถามหา paper “ในสองปีที่ผ่านมา” คำตอบดูถูกต้อง แต่ trace บอกว่า model ค้นด้วยปีที่เก่าเกินไป เพราะมันไม่รู้ว่าวันนี้วันที่เท่าไร แก้ด้วยการบอกวันที่ใน system prompt

③ Provide good tools

Model ไม่เห็นโค้ดของ tool เห็นแค่ชื่อ คำอธิบาย และชนิดของ argument เหมือนกล่องเครื่องมือที่ไม่มีป้าย หยิบผิดชิ้นก็ไม่แปลก

ตำราบอกว่า tool ที่คำอธิบายคลุมเครือจะถูกใช้ผิด ส่วน tool ที่ schema ชัดจะถูกเลือกใช้ถูก และเรียก tool ที่ดีว่า force multiplier คือตัวคูณที่ทำให้ model ตัวเดิมทำงานได้ดีขึ้นหลายเท่า

ใน Lab 1: tool ที่มี argument ชื่อ n ทำให้ model ส่ง n=10 มาทุกรอบ (ได้ paper ที่เก่ากว่า 2023 ติดมา 5 ฉบับทุกรอบ) พอตั้งชื่อเป็น year_from และเขียนคำอธิบายให้ชัด model ส่ง year_from=2023 ถูกทั้ง 5 รอบ

④ Plan for failure

ทุก tool call ล้มเหลวได้ เช่น API timeout หรือผู้ให้บริการตอบว่าเรียกถี่เกินไป (429) ตำราบอกให้สร้าง retry, fallback และ graceful degradation ไว้ที่ ระดับ harness เพื่อให้ model ไม่ต้องคิดเรื่องปัญหาของระบบ

Retry เหมือนโทรหาเพื่อนแล้วสายไม่ว่าง เรารอสักพักแล้วค่อยโทรใหม่ ไม่ใช่กดซ้ำรัวๆ ถ้าทุกทางปิด ระบบก็ยังไม่ควรล่มทั้งระบบ แต่ตอบจากข้อมูลเก่าใน cache แล้วบอกตรงๆ ว่าอาจไม่ใหม่ นี่คือ graceful degradation

หมายเหตุข้อ ③ กับ ④ ทำงานคู่กัน

ถ้าระบบล่ม harness จัดการเองเงียบๆ แต่ถ้า model ใช้ tool ผิด ต้องส่ง error ที่ชัดกลับไปให้ model แก้

ใน Lab 1: retry ใน harness รอ 1 วินาที แล้ว 2 วินาที ก่อนลองใหม่ เมื่อทุกทางปิดจะตอบจากสำเนาคลัง paper แต่ model ตัดคำเตือน “ข้อมูลอาจไม่ใหม่” ทิ้งทุกครั้งที่เราทดสอบ harness จึงต้องแปะคำเตือนเอง

⑤ Use structured outputs

ใช้ JSON schema หรือ function calling บังคับรูปแบบคำตอบ agent ที่ตอบเป็นข้อความอิสระแล้วเราต้องใช้ regex ไล่แกะจะเปราะบาง ส่วน agent ที่ตอบเป็น JSON ที่ตรวจแล้วจะทนทาน เหมือนแบบฟอร์มที่มีช่องให้กรอก เทียบกับจดหมายที่เขียนอะไรมาก็ได้ เรื่องนี้เราลงมือแล้วใน EP02

⑥ Test with diverse inputs

พฤติกรรมของ agent ไม่นิ่งเท่าแชตธรรมดา prompt เดียวกันรันสองรอบอาจเรียก tool คนละลำดับ ตำราจึงแนะนำให้ทดสอบแบบหาเรื่อง ด้วย edge case คำขอที่กำกวม และ input ที่ผิดรูป เหมือนทดสอบเครื่องคิดเลข ไม่ใช่กดแค่ 2 + 2 แต่ต้องลองหารด้วยศูนย์

ใน Lab 2: ชุดทดสอบ 7 แบบ แบบละ 3 รอบ เจอบั๊กที่เราไม่ได้คิดไว้ คำขอหัวข้อที่ไม่มีในคลัง paper พังทุกรอบ และ trace ชี้ว่าสาเหตุคือระบบค้นหาของเราเอง ไม่ใช่ model (find_papers ถือว่าเจอถ้าคำเดียวในชื่อตรงกัน คำว่า “learning” จึงดึง Chronos มา) หลังแก้ ผ่าน 21/21

เลือก pattern: สามคำถาม

ตำราให้ดูสามเรื่องก่อนเลือก pattern (Roitman 2026, หมวด 19.4)

  1. โครงสร้างของงานคาดเดาได้แค่ไหน รู้ขั้นตอนล่วงหน้าไหม
  2. จ่าย LLM call ได้กี่ครั้ง ทั้งเวลาที่ผู้ใช้ต้องรอ และค่าใช้จ่าย
  3. คุณภาพต้องอาศัยการทำซ้ำไหม

ตาราง 19.3: decision matrix

ตำราสรุปทุก pattern ไว้ในตารางเดียว ใช้เป็น decision matrix ได้ เก้าแถวนี้คือทุกอย่างที่เราเรียนใน EP04 และ EP05 (ยกเว้น multi-agent ที่จะเรียนในตอนหลัง)

วิธีใช้คือ เริ่มจากแถวบนสุด แล้วขยับลงเมื่อแบบที่ง่ายกว่าพังให้เห็นจริงๆ เท่านั้น เช่น งานหา paper ห้าฉบับแล้วสรุป ลอง chain ก่อน ถ้าพังเพราะไม่รู้ว่าต้องค้นกี่รอบ ค่อยลงไปใช้ ReAct

ใน Lab 3: เราสร้างตัววัดจำนวน LLM call และค่าใช้จ่าย แล้วลอง prompt chaining (แถวบน) กับ ReAct (แถวกลาง) กับสองโจทย์

  • งาน A สรุป PatchTST สามข้อ: chain ถูกทุกรอบด้วย 2 LLM calls ReAct ก็ถูกแต่ใช้ 3 calls และแพงกว่าราว 3 เท่า จึง หยุดที่แถวบน
  • งาน B หา paper ตั้งแต่ปี 2023 ที่ได้คะแนน ≥ 4.5: chain ผิดทุกรอบ และผิดแบบเงียบๆ เพราะอ่านแค่ผลแรก ReAct ถูกทุกรอบ จึง ขยับลงหนึ่งแถว

ขั้นแรกของ chain ใช้ structured output (หลักข้อ ⑤)

สำคัญประกอบกันได้ แต่รู้จักหยุด

Pattern ทั้งหมดประกอบกันได้ planning agent หนึ่งตัวอาจใช้ chaining ในแต่ละขั้น ใช้ evaluator-optimizer ตอนตรวจทาน และใช้ routing ส่งงานย่อย แต่ตำราปิดท้ายว่า ศิลปะอยู่ที่การรู้ว่าเมื่อไรควรหยุดเพิ่มชั้น

เขียนเอง vs framework

ใน Lab 4 เราทำหลักทั้งหมดอีกครั้งด้วย LangChain (langchain==1.4.7) แต่ละชิ้นตรงกับโค้ดที่เขียนเองใน Lab 1–3

โค้ดสั้นลงมาก แต่ framework ไม่ได้ตัดสินใจแทนเราว่า error แบบไหนควร retry จะเรียง middleware อย่างไร และผู้ใช้ต้องเห็นอะไร การตัดสินใจเหล่านี้ยังเป็นของคนออกแบบ

คำศัพท์ในตอนนี้

Lab

คลัง paper และ search API ที่ล่มเป็นข้อมูลจำลองเพื่อการสอน ส่วน output ของ model ในวิดีโอมาจากการรันจริง ผลที่คุณรันเองจึงอาจต่างไปบ้าง เช่นจำนวน call ของ ReAct ในแต่ละรอบ

คำถามทบทวน

  1. ทำไม prompt chain ที่แก้ปัญหาได้จึงดีกว่า multi-agent system ที่อาจจะแก้ได้
  2. ถ้า agent ตอบว่า “ไม่มีงานวิจัยเรื่องนี้” ทั้งที่มี เราจะใช้ trace หาสาเหตุอย่างไร
  3. จาก ตารางที่ 6.1 error message แบบขวามือช่วย model อย่างไร
  4. Timeout ของ API กับการที่ model ส่ง argument ผิด ควรจัดการต่างกันอย่างไร
  5. ทำไมต้องรันแต่ละ input ในชุดทดสอบซ้ำหลายรอบ
  6. ใน Lab 3 ทำไมงาน A จึงหยุดที่ prompt chaining แต่งาน B ต้องขยับลงไปใช้ ReAct
  7. Middleware ตัวไหนของ LangChain ทำหน้าที่แทน retry loop ที่เราเขียนเองใน Lab 1
