วัตถุประสงค์การเรียนรู้

เมื่อจบตอนนี้ ผู้เรียนจะสามารถ

  1. อธิบายสามข้อจำกัดของความรู้ใน model และสิ่งที่ RAG เพิ่มให้ คือบัตรห้องสมุดของนักวิชาการที่เรียนจบมาหลายปีแล้ว
  2. เลือกระหว่าง RAG, fine-tuning และ long context ให้เหมาะกับงาน
  3. อธิบายสองสายงานของ RAG: indexing ครั้งเดียว และค้นแล้วตอบสำหรับทุกคำถาม
  4. ใช้ embedding และ cosine similarity หาชิ้นเอกสาร top-k ของคำถาม
  5. เขียน prompt ที่บังคับให้ model ตอบจากเอกสารเท่านั้น อ้างที่มา และบอกเมื่อเอกสารไม่มีคำตอบ
  6. เปรียบเทียบ sparse (BM25) กับ dense retrieval และรวมสองแบบด้วย Reciprocal Rank Fusion
  7. เลือกวิธีตัดชิ้น (ขนาดคงที่ + overlap, ตามโครงสร้าง, parent-child) และวัดผลแทนการเดา

model ตอบจากตำราของเราได้ไหม

ใน EP09 Lab 3 เราถามถึง paper ในคลังของเรา แต่ model ไม่ได้เปิดอ่านเลย มันตอบจากชื่อ paper กับสิ่งที่รู้มาเอง คำตอบฟังดูดี แต่เราไม่รู้ว่ามาจากไหน ตอนนี้เริ่มโมดูล M3 · RAG ด้วยคำถามเดียว: จะทำให้ model ตอบจากเอกสารของเราจริงๆ และบอกได้ว่าคำตอบมาจากหน้าไหน ได้อย่างไร

สามข้อจำกัด และความรู้สองแบบ

model เก็บความรู้ไว้ใน weight ของมันเอง ซึ่งถูกบีบอัดมาตอนฝึก ตำราบอกว่าสิ่งนี้มาพร้อมสามข้อจำกัด (Roitman 2026, หมวด 16.1):

  1. Hallucination (EP02): ถามเกินสิ่งที่มันรู้แน่ มันก็ยังตอบอย่างมั่นใจ
  2. ความรู้เก่า (staleness): ข้อมูลที่ใช้ฝึกมีวันตัด ตำราที่เราเรียนออกปี 2026 หลังจากที่ model ของเราถูกฝึก
  3. ไม่รู้เรื่องเฉพาะทาง (domain specificity): model ทั่วไปไม่เคยเห็นเอกสารภายในบริษัท ระเบียบของมหาวิทยาลัย หรือ code ของเรา

ความรู้ใน weight เรียกว่า parametric ความรู้ในเอกสารนอก model เรียกว่า non-parametric ตำราให้ภาพที่จำง่าย: model ธรรมดาเหมือนนักวิชาการที่จำห้องสมุดทั้งห้องได้ แต่เรียนจบมาหลายปีแล้ว RAG (retrieval-augmented generation) ให้บัตรห้องสมุดกับนักวิชาการคนนั้น ค้นได้ทันที อ้างที่มาได้ และยอมรับว่าต้องไปเปิดดูก่อน แทนที่จะเดาจากความจำ

ใน Lab 1 ถามโดยไม่มี RAG ว่าตำราใช้อุปมาอะไรอธิบาย RAG, Gemma ตอบอย่างมั่นใจว่า “การสอบแบบเปิดตำรา” ซึ่งไม่มีอยู่ในหน้าไหนของตำราเลย พอมี RAG มันตอบว่า “บัตรห้องสมุด” อ้าง Doc 2 หน้า 295

RAG, fine-tuning หรือ long context

RAG ไม่ได้มาแทน fine-tuning: fine-tuning สอนให้ model รู้ว่าจะคิดและตอบอย่างไร ส่วน RAG ให้สิ่งที่จะเอามาคิด เหมือนฝึกพ่อครัว กับส่งวัตถุดิบสดทุกเช้า ทั้งสองอย่างทำงานด้วยกัน

สองสายงาน: เตรียมคลังครั้งเดียว ตอบได้ทุกคำถาม

เก็บ metadata (ไฟล์ไหน หน้าไหน) ไว้ด้วย เพราะเป็นสิ่งที่ทำให้คำตอบอ้างที่มาได้ เหมือนห้องสมุด บัตรรายการทำครั้งเดียวตอนหนังสือเข้ามา แล้วใช้ตอบทุกคนที่มาถาม

Embedding และ cosine similarity

Embedding model แปลงข้อความเป็นรายการตัวเลขที่แทนความหมาย ของเราได้ 4,096 ตัว ข้อความที่ความหมายใกล้กันได้เวกเตอร์ที่ชี้ไปทางเดียวกัน Cosine similarity วัดว่าสองเวกเตอร์ชี้ไปทางเดียวกันแค่ไหน แล้ว top-k เก็บ k ชิ้นที่ได้คะแนนสูงสุดของคำถามนั้น

ใน Lab 1 car·automobile ได้ราว 0.95 แต่ car·banana ก็ยังได้ราว 0.58 ไม่ใช่ศูนย์ ข้อความที่ไม่เกี่ยวกันมักได้คะแนนค่อนข้างสูง สิ่งที่เราใช้จริงจึงเป็นลำดับ ไม่ใช่ตัวเลขตัวเดียว

Generation: ตอบจากเอกสารเท่านั้น

Listing 16.1 ให้ prompt ที่มีสามกฎ: ตอบจาก context ที่ให้เท่านั้น ถ้า context ไม่พอให้บอกตรงๆ และอ้างที่มาเป็น [Doc n] แต่ละชิ้นใน prompt มีเลข Doc ชื่อไฟล์ และเลขหน้ากำกับ คำตอบว่า “เอกสารไม่ได้บอก” ไม่ใช่ความล้มเหลว แต่เป็นสิ่งที่เราต้องการพอดี

ใน Lab 1 ถามเมืองหลวงของออสเตรเลีย model ตอบว่า context ไม่มีข้อมูลนี้ ทั้งที่มันรู้คำตอบ คลังของเราไม่ได้พูดถึงออสเตรเลีย มันจึงไม่ตอบจากความจำ

Sparse, dense และ hybrid retrieval

Sparse retrieval ให้คะแนนชิ้นเอกสารจากคำในคำถามที่ปรากฏในชิ้นนั้น เหมือนดัชนีท้ายเล่ม ตัวที่ใช้กันมากที่สุดคือ BM25: คำหายากมีน้ำหนักมากกว่า คำที่ซ้ำหลายครั้งช่วยได้แต่ค่อยๆ อิ่มตัว และชิ้นที่ยาวมากเสียคะแนนนิดหน่อย มันชนะเรื่องรหัส error ชื่อเฉพาะ และคำหายากหรือคำใหม่ ไม่ต้องใช้ GPU และอธิบายได้ง่าย แต่ถ้าคำถามว่า “car” มันจะหา “automobile” ไม่เจอ

Dense retrieval ใช้ embedding (ตัวอย่างในตำราคือ DPR ที่มี encoder ของคำถามกับของเนื้อหาแยกกัน) มันจับความหมายได้ ถามว่าจะแบ่งเอกสารยาวอย่างไร มันก็เจอชิ้นที่พูดถึง chunking เมื่อมีหลายล้านชิ้นก็ค้นแบบประมาณ (เช่นด้วย FAISS) Table 16.2 เทียบวิธีอื่นๆ อีกหลายวิธี cross-encoder แม่นที่สุดแต่ช้า จึงใช้เรียงลำดับใหม่หลังค้นมาแล้ว (EP11)

Hybrid ใช้ทั้งสองแบบแล้วรวมผล แต่คะแนนของสองระบบอยู่คนละสเกล ตำราจึงใช้ Reciprocal Rank Fusion ที่ดูแค่อันดับ:

\[\text{RRF}(d) = \sum_{\text{lists}} \frac{1}{60 + \text{rank}(d)}\]

อันดับ 3 ใน BM25 และอันดับ 7 ใน dense ได้ 1/63 + 1/67 ≈ 0.0308 อันดับหนึ่งทั้งสองฝั่งได้ ≈ 0.0328 เลข 60 ช่วยไม่ให้อันดับต้นๆ มีน้ำหนักมากเกินไป

ใน Lab 2 เราเขียน BM25 และ RRF เอง RRF ได้ 0.0308 และ 0.0328 ตรงกับตำรา “What is PLAID?”: BM25 เจอที่อันดับ 1 แต่ dense ให้ไว้ราวอันดับ 99 ส่วนคำถามเรื่อง parent-child ที่ถามด้วยคำอื่น dense เจอหน้า 302–303 แต่ BM25 พลาด วัด hit@3 บน 10 คำถาม: BM25 4, dense 4, hybrid 8 ดีขึ้นโดยรวม แต่ไม่ใช่ทุกข้อ มีสองข้อที่แย่ลง

Chunking

ตำราบอกว่าการตัดชิ้นเป็นหนึ่งในการตัดสินใจที่มีผลมากที่สุดในระบบ RAG (Roitman 2026, หมวด 16.4) ชิ้นที่ดีควรเล็กพอสำหรับ embedding model พูดเรื่องเดียว และอ่านแยกออกมาแล้วยังเข้าใจได้

  • ขนาดคงที่ + overlap: ตัดทุก W token ชิ้นติดกันใช้ O token ร่วมกัน ประโยคที่ถูกตัดตรงรอยต่อจะครบในชิ้นใดชิ้นหนึ่ง เอกสาร 1,000 token ที่ W = 512 และ O = 64 ได้ ⌈(1000 − 64) / (512 − 64)⌉ = 3 ชิ้น (สมการ 16.19)
  • ตามความหมาย (semantic): ตัดตรงที่ประโยคข้างเคียงเริ่มไม่คล้ายกัน
  • ตามโครงสร้าง: ตัดที่หัวข้อ ฟังก์ชัน หรือ class และไม่ตัดตารางกลางแถว
  • Parent-child: ค้นด้วยชิ้นเล็ก (แม่น) แต่ส่งชิ้นใหญ่ที่ครอบอยู่ให้ model (บริบทพอ)

ใน Lab 3 สมการ 16.19 ตรงกับลูปของเราใน Lab 1 ทุกหน้า และในแบบฝึกหัด การไม่ใช้ overlap เลยกลับได้คะแนนสูงกว่าบนคำถามชุดนี้ ไม่มีกฎข้อไหนแทนการวัดผลได้

RAG ตัวเดิมด้วย LangChain

ใน Lab 4 มีค่าเริ่มต้นสามจุดที่ไม่ขึ้น error เลย Listing 16.2 ตามที่เขียนนับเป็นตัวอักษร ไม่ใช่ token ได้ 408 ชิ้น ราว 115 token แทนที่จะเป็น 141 ชิ้น OpenAIEmbeddings ส่ง token id ไป ซึ่ง OpenRouter ตอบกลับเป็น 400 ถ้าไม่ตั้ง check_embedding_ctx_length=False และ EnsembleRetriever รวมได้แค่สิ่งที่ retriever แต่ละตัวส่งมา list ละ 3 ได้ 13/20 list ละ 60 ได้ 17/20 เราจับได้ทั้งสามจุดเพราะรู้ว่าข้างในทำงานอย่างไร และวัดผลทุกครั้ง

มีคำถามหนึ่งที่พลาดทุกวิธี: คำถามเรื่องอุปมาแบบยาว ที่มีชื่อผู้แต่งและชื่อตำราอยู่ด้วย ชิ้นที่มีบัตรห้องสมุดอยู่อันดับ 8 ด้วย dense อันดับ 5 ด้วย hybrid และอันดับ 17 ด้วย parent-child คำในคำถามดึงมันไปหาหน้าอื่น วิธีแก้คือแปลงคำถามก่อนค้น ซึ่งอยู่ใน EP11
