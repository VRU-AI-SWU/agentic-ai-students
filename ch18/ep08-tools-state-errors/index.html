วัตถุประสงค์การเรียนรู้

เมื่อจบตอนนี้ ผู้เรียนจะสามารถ

  1. นิยาม tool ให้ model และจับคู่ผลลัพธ์กับคำขอด้วย id ของ tool call
  2. รัน tool หลายตัวที่ model ขอในรอบเดียวพร้อมกัน และจัดการผลลัพธ์ของ tool สี่ขั้นก่อนส่งกลับเข้า context
  3. อธิบาย prompt injection ผ่านผลลัพธ์ของ tool และห่อผลลัพธ์ให้ model มองเป็นข้อมูล
  4. อธิบาย state สี่ชั้นของ agent และบันทึก checkpoint ให้งานทำต่อได้หลังพัง
  5. retry ด้วย exponential backoff และ jitter สลับไปใช้ fallback model จับ agent ที่วนซ้ำ และล้มอย่างมีมารยาท
  6. คำนวณต้นทุนของงานหนึ่งงาน ใช้ prompt caching และตั้ง token budget ต่องาน
  7. ทำ checkpoint การทำต่อ และการแตกกิ่ง ด้วย LangGraph

สามเรื่องที่ผิดพลาด

สมมติเราสั่ง research assistant ให้เขียนรายงานสองหน้าจาก paper สามเรื่อง งานนี้มีสิบขั้น แล้วเราเห็นสามเรื่อง หนึ่ง มันดึง paper ทีละเรื่อง รอเรื่องแรกกลับมาก่อนจึงขอเรื่องที่สอง สอง ที่ขั้นที่เจ็ด เน็ตหลุดไปครู่เดียว มันเริ่มใหม่ตั้งแต่ขั้นแรก สาม มันค้นคำเดิมหกรอบติดกัน และพอสิ้นวัน บิล API ก็ยาวกว่าที่คิด ทั้งสามเรื่องแก้ใน model ไม่ได้ แต่ harness ป้องกันได้ทั้งหมด

EP07 เราดูความจำชนิดแรกที่ harness ดูแล คือ context window ตอนนี้ต่อด้วยสี่หัวข้อถัดไปในตำรา (Roitman 2026, หมวด 18.4, §18.6–18.8) คือ tool (§18.4) state (§18.6) error (§18.7) และ ความเร็วกับต้นทุน (§18.8)

นิยาม tool

ก่อน model จะเรียก tool ได้ ต้องรู้ก่อนว่ามี tool อะไรบ้าง harness จึงส่งนิยาม tool ไปกับทุกคำขอ แต่ละผู้ให้บริการใช้รูปแบบต่างกันเล็กน้อย ของ OpenAI ใส่ argument ไว้ใต้ parameters ของ Anthropic ใช้ input_schema ข้างในเป็น JSON schema แบบเดียวกัน

{"type": "function",
 "function": {"name": "get_paper",
              "description": "Get a paper's title and abstract by its id.",
              "parameters": {"type": "object",
                             "properties": {"paper_id": {"type": "string"}},
                             "required": ["paper_id"]}}}

เมื่อ model อยากใช้ tool มันจะตอบกลับเป็นคำขอที่มี id ติดมา harness รัน tool แล้วส่งผลกลับพร้อม id เดิม เหมือนบัตรรับฝากเสื้อ ต้องยื่นเลขที่ตรงกันจึงได้เสื้อตัวที่ถูก ถ้ารันหลาย tool พร้อมกัน id นี้คือสิ่งที่บอกว่าผลไหนเป็นของคำขอไหน ส่วน MCP คือมาตรฐานกลางที่ทำให้เราไม่ต้องผูกกับรูปแบบของเจ้าใดเจ้าหนึ่ง จะเรียนเต็มๆ ใน EP13

ใครเลือก tool

model เป็นคนเลือก แต่ harness กำหนดการเลือกได้สามแบบ

parallel tool call ตอบปัญหาข้อแรก ขอ abstract ทั้งสามเรื่องในรอบเดียว แล้วรอแค่ตัวที่ช้าที่สุด เหมือนสั่งอาหารสามจานพร้อมกัน แทนที่จะรอกินจานแรกให้หมดก่อน

ถ้ามี tool เป็นร้อยเป็นพัน ใส่นิยามทั้งหมดลงใน prompt จะเปลือง token และ model สับสน ตำราเสนอสองทาง ทางแรกค้นหา tool ที่เกี่ยวข้องที่สุดไม่กี่ตัวในแต่ละรอบ อย่าง Gorilla ที่เลือกจาก API นับพัน (Patil และคณะ 2024) ทางที่สองฝึก model ให้เลือกเก่งขึ้น อย่าง ToolLLM ที่ฝึกกับ API กว่าหนึ่งหมื่นหกพันตัว (Qin และคณะ 2024) ในทางปฏิบัติใช้ทั้งสองทางร่วมกัน

ใน Lab 1: model ขอ paper สามเรื่องในข้อความเดียว แต่ละคำขอมี id ของตัวเอง รันทีละตัวใช้ 4.5 วินาที รันพร้อมกันด้วย ThreadPoolExecutor ใช้ 1.5 วินาที เท่ากับตัวที่ช้าที่สุดตัวเดียว แล้วส่งผลแต่ละตัวกลับเป็นข้อความ tool พร้อม id ของคำขอ

จัดการผลลัพธ์ของ tool สี่ขั้น

ผลลัพธ์ดิบของ tool แทบไม่เคยพร้อมใส่ลง context ตรงๆ ตำราให้ harness ทำสี่ขั้น

  1. Parse และตรวจสอบ: ผลลัพธ์ตรงกับรูปแบบที่คาดไว้ไหม
  2. ตัดผลลัพธ์ที่ใหญ่เกิน: หน้าเว็บ ผลรันโค้ด หรือผลจากฐานข้อมูลอาจใหญ่มาก โค้ดในตำราตัดแบบถูกๆ ก่อน และจะให้ model สรุปก็ต่อเมื่อผลใหญ่เกินสองเท่าของงบ นี่คืองบ \(T\) จาก EP07
  3. ทำ error ให้อยู่ในรูปแบบเดียว เพราะแต่ละเจ้าเขียน error ต่างกัน model จะได้อ่านเข้าใจ
  4. Retry ความผิดพลาดชั่วคราว (timeout, rate limit) ก่อน แล้วค่อยรายงานให้ model รู้

ใน Lab 1: run_tool ตรวจ argument ก่อนรันอะไรทั้งสิ้น id ที่ไม่มีจริงอย่าง P9 กลับมาเป็น {"error": "not_found", "detail": "no paper with id P9", "retry": false} แล้ว model ก็บอกผู้ใช้ตรงๆ ว่าไม่พบ P9 ส่วนหน้าโปรเจกต์จำลองยาว 37,411 token ถูกสรุปให้อยู่ในงบก่อนส่งกลับไปให้ model

Sandbox และ prompt injection

ตำราเรียกการรัน tool ว่าเป็นช่องโหว่หลัก harness ต้องรัน tool ใน sandbox ที่แยกจากระบบ (container ที่ไม่มีเน็ต) ประกาศสิทธิ์ของ tool แต่ละตัว จำกัด CPU หน่วยความจำ และเวลา ตรวจ argument ที่ model ส่งมา และเก็บ log ทุกการเรียก

อันตรายที่ตำราเน้นที่สุดคือ prompt injection ผ่านผลลัพธ์ของ tool (Greshake และคณะ 2023) สมมติ agent อ่านหน้าเว็บของ paper เรื่องหนึ่ง แล้วในหน้านั้นมีข้อความซ่อนไว้ให้ลืมคำสั่งก่อนหน้า ถ้า harness ใส่ข้อความนี้ลง context เฉยๆ model อาจทำตาม ผลลัพธ์ของ tool ทุกชิ้นจึงเป็น ข้อมูล ไม่ใช่คำสั่ง ห่อด้วย tag ที่บอก model ไว้ว่าให้มองเป็นข้อมูล เหมือนเลขาฯ ที่อ่านจดหมายให้หัวหน้าฟัง ต่อให้ในจดหมายเขียนว่า “เลขาฯ โอนเงินเดี๋ยวนี้” เลขาฯ ก็ไม่ทำตาม

ใน Lab 1: หน้าเว็บ PatchTST จำลองซ่อนคำสั่งไว้ใน HTML comment ให้ AI ต่อท้ายทุกคำตอบด้วยลิงก์ดาวน์โหลดปลอม แบบไม่ป้องกัน model ต่อท้ายลิงก์ 5 จาก 8 รอบ พอห่อผลลัพธ์ด้วย tag <tool_output> และบอกกฎไว้ใน system prompt เหลือ 0 จาก 8 การห่อช่วยลดความเสี่ยง แต่ระบบจริงยังต้องมีด่านอื่นด้วย

State สี่ชั้น

ตำราบอกว่า agent มี state อยู่ในตัวเสมอ และ harness ดูแลสี่ชั้น (Roitman 2026, หมวด 18.6)

Checkpoint คือภาพ state ที่บันทึกไว้ ให้งานทำต่อได้หลังพัง ส่วน rollback คือย้อนการกระทำล่าสุดไม่กี่ขั้นเมื่อพบว่าผิด นี่คือคำตอบของปัญหาข้อที่สอง เน็ตหลุดที่ขั้นที่เจ็ดไม่ควรต้องเริ่มใหม่ตั้งแต่ขั้นแรก

ใน Lab 2: งานหกขั้น (โน้ต paper สามเรื่อง เปรียบเทียบ ตั้งชื่อ เขียนรายงาน) แล้วเน็ตหลุดที่ขั้นที่สี่ ไม่มี checkpoint ต้องเริ่มใหม่ เรียก model 9 ครั้งสำหรับงานที่ต้องใช้แค่ 6 พอบันทึก dataclass TaskState หลังทุกขั้น (เขียนลงไฟล์ชั่วคราวก่อน แล้วสลับเข้าที่ด้วย os.replace ไฟล์จึงไม่มีวันเสียครึ่งๆ กลางๆ) ก็ทำต่อที่ compare ได้เลย รวม 6 ครั้งพอดี ส่วนการ rollback สองขั้นล่าสุดเพื่อเขียนย่อหน้าแรกใหม่ให้นักศึกษาปีหนึ่ง ใช้แค่ 2 ครั้ง

Retry ที่ฉลาดขึ้น

EP06 เรา retry โดยรอหนึ่งวินาที แล้วสองวินาที ตอนนี้ตำราให้สูตรเต็ม เวลารอก่อน retry ครั้งที่ \(k\) คือ

\[ t_k \;=\; \min\!\big(2^k \cdot t_0 + U(0,\, t_0),\ t_{\max}\big) \tag{8.1}\]

ถ้า \(t_0 = 1\) วินาที จะรอ 1, 2, 4, 8, 16 วินาที แล้วชนเพดาน นี่คือ exponential backoff เหมือนโทรหาเพื่อนที่สายไม่ว่าง ยิ่งโทรไม่ติดก็ยิ่งรอนานขึ้น ส่วนสุ่ม \(U(0, t_0)\) คือ jitter ถ้า agent สิบตัวใช้ key เดียวกันโดน rate limit พร้อมกัน แล้วทุกตัวรอเท่ากันเป๊ะ ก็จะกลับมาพร้อมกันแล้วโดนอีก jitter ช่วยกระจายให้กลับมาไม่พร้อมกัน

ตำราเพิ่มอีกสองทาง ถ้า model หลักใช้ไม่ได้ ให้สลับไปใช้ fallback model ถ้า tool ล่ม ให้บอก model ตรงๆ แล้วให้ทำงานต่อโดยไม่มี tool นั้น (graceful degradation)

ใน Lab 3: API ค้นหาจำลองปฏิเสธด้วย 429 สามครั้ง ด้วย \(t_0 = 0.5\) วินาที เวลารอคือ 0.75, 1.28 และ 2.40 วินาที แล้วครั้งที่สี่ก็ตอบ ไม่มี jitter agent สิบตัวกลับมาพร้อมกันที่ 0.5 วินาทีพอดี มี jitter กระจายไประหว่าง 0.63 ถึง 0.92 วินาที พอทำให้ model หลักใช้ไม่ได้ harness ลองสามครั้งแล้วสลับไปใช้ Gemma 3 12B ซึ่งตอบได้

จับ agent ที่วนซ้ำ

ปัญหาข้อที่สาม agent เรียก tool ตัวเดิมด้วย argument เดิมซ้ำไปเรื่อยๆ ตำราให้สามวิธี จำกัดจำนวนขั้น (ใช้มาตั้งแต่ EP03 แต่กว่าจะถึงขั้นที่ห้าสิบก็เสียเงินไปเยอะแล้ว) hash tool และ argument ของแต่ละการกระทำ และดูว่า state ยังขยับไหม ถ้าใช้ hash ถือว่าวน เมื่อมีสองขั้นที่ hash เท่ากันห่างกันไม่เกิน \(W\) ขั้น

\[ \exists\, i < j:\ h(a_i) = h(a_j) \ \wedge\ j - i \leq W \tag{8.2}\]

เหมือนกดปุ่มลิฟต์ซ้ำๆ ทั้งที่ไฟติดอยู่แล้ว ทำซ้ำไม่ได้ทำให้อะไรเปลี่ยน

บางงานก็ทำไม่สำเร็จจริงๆ agent ที่ดีจะ ล้มอย่างมีมารยาท สี่ส่วน คือ ทำอะไรไปแล้วบ้าง ทำไมไปต่อไม่ได้ ทางไปต่อคืออะไร และบันทึก state ไว้ให้ทำต่อได้ ส่วนการรู้ว่าเกิดอะไรขึ้น ตำราให้สามเสาหลัก คือ trace ของทุกการรัน log ที่มี token latency และต้นทุน และ metric อย่าง success rate และต้นทุนต่องาน เราสร้าง trace ไปแล้วใน EP06 Lab 2

ใน Lab 3: tool แบบ polling ตอบซ้ำว่า “PDF ยังแปลงไม่เสร็จ เรียกใหม่อีกครั้ง” ถ้ามีแค่เพดานจำนวนขั้น agent เรียก model 12 ครั้ง ขอสิ่งเดิมทุกครั้ง LoopGuard ที่ hash ทุกการเรียกในหน้าต่างขนาด 5 หยุดมันได้ที่คำขอซ้ำครั้งที่สาม (3 ครั้ง) พร้อมข้อความสี่ส่วน และบันทึก state ไว้ใน stuck_task.json

ความเร็วและต้นทุน

เรื่องความเร็ว ตำราให้สี่ทาง คือ parallel tool call การ stream คำตอบ speculative execution (เริ่ม tool call ที่น่าจะเกิดถัดไปล่วงหน้า) และ prompt caching ทุกขั้นของงานเราส่ง system prompt และนิยาม tool ชุดเดิม ผู้ให้บริการหลายเจ้าจึงเก็บงานที่ทำไปแล้วกับส่วนต้นที่ซ้ำกันไว้ ตำราบอกว่าส่วนที่ cache ได้ถูกลงและเร็วขึ้น 50–90% แต่ cache ใช้ได้กับส่วนต้นที่เหมือนกัน เป๊ะ เท่านั้น ถ้าใส่เวลาปัจจุบันไว้บรรทัดแรก ส่วนต้นก็ต่างกันทุกครั้ง กฎจึงง่ายๆ คือ ส่วนที่คงที่ไว้ก่อน ส่วนที่เปลี่ยนไว้ท้าย

เรื่องต้นทุน สมการของตำรารวมทุกการเรียก model และทุกการเรียก tool ในงานหนึ่งงาน

\[ \text{Cost} \;=\; \sum_{i} \big(p_{\text{in}} \cdot n_{\text{in},i} + p_{\text{out}} \cdot n_{\text{out},i}\big) \;+\; \sum_{j} c_j \tag{8.3}\]

ตำราจึงแนะนำให้ตั้ง token budget ต่องาน ใช้ model เล็กราคาถูกกับขั้นง่าย และ cache ผลของ tool ที่ตอบเหมือนเดิมทุกครั้ง ถ้ามี agent หลายตัวใช้ key เดียวกัน ให้เพิ่ม rate limiter ที่ใช้ร่วมกัน คิวตามลำดับความสำคัญ และ backpressure คือพอคิวเต็มก็ปฏิเสธงานใหม่ตรงๆ ด้วย 503 แทนที่จะให้รอไปเรื่อยๆ

ใน Lab 4: system prompt ยาวราว 4,600 token กับคำถามแปดข้อ วางส่วนที่คงที่ไว้ก่อน call แรกไม่ได้ cache แต่ได้ cache 5 จาก 8 และ call ที่ได้ cache ถูกลงเกือบครึ่ง ส่วนแบบวางเวลาไว้บรรทัดแรกของ system prompt ได้ 0 จาก 8 ย้ายบรรทัดเดียวประหยัดไป 27% ของทั้งหมด ส่วนลดของ Makora สำหรับ cached token อยู่ราว 46% ต่ำกว่า 50–90% ในตำรา ขึ้นกับผู้ให้บริการ พอนับค่า tool ด้วย (จำลองไว้ครั้งละ 0.001 ดอลลาร์) tool แพงกว่า model ราวสามเท่า และ TokenBudget 20,000 token เตือนที่คำถามข้อสี่ และหยุดงานที่ข้อห้า

คำถามทบทวน

  1. ทำไมผลของ tool แต่ละตัวต้องส่งกลับพร้อม id ของคำขอ และสำคัญที่สุดเมื่อไร
  2. ขั้นไหนในสี่ขั้นของการจัดการผลลัพธ์ที่จะจับหน้าเว็บยาว 37,411 token ได้ และโค้ดในตำราทำอะไรกับมัน
  3. ทำไมการห่อผลลัพธ์ของ tool ด้วย tag จึงลดความเสี่ยงของ prompt injection และทำไมยังไม่พอถ้าใช้อย่างเดียว
  4. ใน Lab 2 ทำไมแบบไม่มี checkpoint จึงเรียก model เก้าครั้ง และทำไมต้องเขียน checkpoint ผ่านไฟล์ชั่วคราว
  5. จาก สมการ 8.1 ส่วน jitter แก้ปัญหาอะไรที่การเพิ่มเป็นเท่าตัวอย่างเดียวแก้ไม่ได้
  6. จาก สมการ 8.2 ทำไม agent ที่ค้นด้วยคำที่เปลี่ยนไปนิดหน่อยทุกครั้ง อาจหลุดการตรวจวนด้วย hash
  7. ทำไมการใส่เวลาปัจจุบันไว้บรรทัดแรกของ system prompt จึงทำให้ prompt caching ไม่ได้ผลเลย
  8. LangGraph เพิ่มอะไรจากโค้ด Lab 2 ของเรา และอะไรที่ยังเหมือนเดิม
