EP07 Context Window Management

§18.1–18.3 · agent harness · context budget · silent truncation · การบีบ history · recursive decomposition · prompt architecture

วัตถุประสงค์การเรียนรู้

เมื่อจบตอนนี้ ผู้เรียนจะสามารถ

  1. อธิบายได้ว่า agent harness ทำอะไร และทำไม context window จึงเป็นงานของ harness
  2. เขียน context budget ของ agent เป็นห้าส่วน และเลือกได้ว่าจะแบ่งงบแบบตายตัวหรือแบบ dynamic
  3. อธิบาย silent truncation และเขียน pre-flight token check ด้วย tokenizer ของ model เอง
  4. เปรียบเทียบวิธีบีบ history ได้แก่ FIFO การปักหมุด การให้น้ำหนักความสำคัญ และการสรุปของเก่า
  5. ใช้ recursive context decomposition กับเอกสารที่ใหญ่กว่างบต่อ call
  6. ประกอบ prompt จาก block ที่เปลี่ยนแยกกันได้ และใช้ SummarizationMiddleware ของ LangChain ได้

Agent ที่ลืมคำสั่งแรก

ลองนึกภาพว่าเราคุยกับ research assistant agent มาตั้งแต่เก้าโมงเช้า ข้อความแรกสั่งไว้ชัดว่า “ตอบเป็นภาษาไทย และอ้างอิง paper ทุกครั้ง” ระหว่างนั้นเราแปะ paper เข้าไปทีละเรื่องจนครบสิบสองเรื่อง พอสิบเอ็ดโมง agent เริ่มตอบเป็นภาษาอังกฤษ และไม่อ้างอิงอะไรเลย ที่แปลกคือ log ไม่มี error สักบรรทัด ตอนนี้จะตอบว่าเกิดอะไรขึ้น และ harness ต้องทำอะไรเพื่อไม่ให้เกิดขึ้นอีก

Agent harness

ตำราเรียกโครงสร้างที่ห่อ LLM ไว้ว่า agent harness มันเปลี่ยน model จากเครื่องเติมข้อความที่ไม่จำอะไร ให้เป็น agent ที่มีเป้าหมาย ทำงานหลายขั้น และใช้ tool ได้ (Roitman 2026, หมวด 18.1) ตัว model เป็นแค่ฟังก์ชันที่รับ token แล้วคืน token ไม่มีความจำ เรียก API ไม่ได้ และไม่รู้เวลา ตำราจึงเทียบ harness กับระบบปฏิบัติการที่ให้ร่างกายกับ model

งานจึงแบ่งกันชัด การคิดเป็นของ model ส่วน harness ดูแลการเรียก tool ความจำ การส่งข้อความ และการบันทึกทุกขั้น ใน research assistant ของเรา Gemma เป็นคนคิด แต่ harness เป็นคนเรียก search_papers เก็บบทสนทนา และเก็บ trace (EP06) ความจำส่วนแรกที่ harness ต้องดูแลคือ context window

Context window คือโต๊ะทำงาน

Context window คือ working memory ของ agent ลองนึกถึงโต๊ะทำงาน model อ่านได้เฉพาะกระดาษที่วางบนโต๊ะ กระดาษที่ไม่ได้วาง ต่อให้สำคัญแค่ไหน model ก็มองไม่เห็น และกระดาษทุกแผ่นบนโต๊ะมีต้นทุน ทุก token ที่ส่งไปต้องจ่ายเงินและทำให้รอนานขึ้น การจัดว่าอะไรควรอยู่บนโต๊ะจึงเป็นการตัดสินใจทางวิศวกรรมที่ส่งผลมากที่สุดเรื่องหนึ่งของการออกแบบ agent (Roitman 2026, หมวด 18.2)

Context budget

ตำราเขียนงบของโต๊ะเป็นสมการเดียว ความยาว context สูงสุด \(C\) ต้องรองรับห้าส่วน

\[ C \;\geq\; S + M + T + H + R \tag{31.1}\]

ปัญหาคือ \(C\) คงที่ แต่ \(H\) ยาวขึ้นเรื่อยๆ และบางครั้ง tool คืนผลก้อนใหญ่มาทีเดียว เช่นหน้าเว็บทั้งหน้า วิธีแรกคือแบ่งงบตายตัวเหมือนแบ่งเงินเดือนใส่ซอง ตำราให้ตัวอย่างไว้ \(S\) 10% \(M\) 20% \(T\) 10% \(H\) 50% และ \(R\) 10% ง่ายและคาดเดาได้ แต่เสียพื้นที่เมื่อบางซองใช้ไม่เต็ม อีกวิธีคือแบ่งแบบ dynamic ทุกรอบ ในทางปฏิบัติคือเติมส่วนที่สำคัญที่สุดก่อน แล้วค่อยบีบหรือตัดส่วนที่สำคัญน้อยกว่า

กับดัก silent truncation

API หลายตัวเมื่อได้ข้อความยาวเกิน context จะตัดบางส่วนทิ้งเงียบๆ อาจตัดตรงกลางหรือตั้งแต่ต้น ตำราเรียกว่า silent truncation ผลคือ system prompt อาจหาย model ลืมคำสั่งก่อนหน้า หรือ hallucinate จากข้อมูลที่ขาดไป โดยไม่มีสัญญาณ error ใดๆ ใน research assistant ของเรา ข้อความแรกที่สั่งให้ตอบภาษาไทยและอ้างอิง paper คือท่อนที่ถูกตัดทิ้ง

สำคัญกฎจากตำรา

นับ token ก่อนส่งทุกครั้ง และจัดการตอนที่ล้นให้ชัดเจน อย่าปล่อยให้ API ตัดสินใจแทนเรา

ใน Lab 1: เราส่งบทสนทนายาวราวสองแสนเจ็ดหมื่น token สามแบบ pre-flight check หยุดไว้ก่อนส่ง การส่งตรงๆ ได้ error 400 ที่ชัดเจน แต่ตัวเลือก middle-out ของ OpenRouter ตอบกลับมาปกติ 200 OK ทั้งที่ข้อความตรงกลางหายไปกว่าเก้าหมื่น token model จึงตอบว่าไม่มีข้อมูลกำหนดส่ง harness จับได้ด้วยการเทียบตัวเลขที่นับเองก่อนส่ง กับจำนวน token ที่ API บอกว่าเห็นจริง

บีบ history ① สรุปของเก่า

เมื่อ history เกินงบ harness ต้องบีบให้สั้นลงโดยไม่ทำข้อมูลสำคัญหาย วิธีแรกคือสรุปข้อความเก่าที่สุด \(k\) ข้อความเป็นย่อหน้าเดียว แล้ววางไว้หน้าข้อความล่าสุดที่ยังเก็บไว้ครบ

\[ H' \;=\; \text{Summarize}(H_{1:k}) \,\|\, H_{k+1:n} \tag{31.2}\]

เหมือนเราไม่ฟังเทปเลคเชอร์ทั้งสัปดาห์ซ้ำ แต่อ่านโน้ตสรุปหน้าเดียว เช่น สิบข้อความแรกของ research assistant อาจเหลือแค่ “ผู้ใช้ศึกษา transformer สำหรับ time series ต้องการคำตอบภาษาไทยพร้อมอ้างอิง อ่าน paper ไปแล้วสองเรื่อง” ตำราบอกว่าบทสรุปมักสั้นกว่าต้นฉบับ 5–10 เท่า และใช้ model ที่เล็กกว่า ถูกกว่า มาสรุปแทนก็ได้

บีบ history ② เก็บเฉพาะที่สำคัญ

วิธีที่สองไม่สรุป แต่เลือกเก็บ ตำราเสนอไว้สองแบบ

  • Selective retention: ให้คะแนนแต่ละข้อความจากความเกี่ยวข้องกับคำถามตอนนี้บวกความใหม่ แล้วเก็บ \(k\) ข้อความที่คะแนนสูงสุด การวัดความเกี่ยวข้องต้องใช้เครื่องมือที่จะเรียนในตอน RAG
  • Importance-weighted truncation: ให้น้ำหนัก \(w_i\) กับแต่ละข้อความ ข้อความที่ผู้ใช้แก้ agent หรือผลจาก tool ได้น้ำหนักสูง ส่วนคุยเล่นได้น้ำหนักต่ำ แล้วเลือกเก็บข้อความให้น้ำหนักรวมมากที่สุดภายในงบ

\[ \max_{\mathcal{K}} \sum_{i \in \mathcal{K}} w_i \quad \text{โดยที่} \quad \sum_{i \in \mathcal{K}} |m_i| \leq B_H \tag{31.3}\]

เหมือนจัดกระเป๋าเดินทางที่จำกัดน้ำหนักยี่สิบกิโล เราใส่ของที่คุ้มที่สุดต่อน้ำหนักก่อน ตำราบอกว่านี่คือโจทย์ 0/1 knapsack และแก้แบบ greedy ได้ โดยเรียงข้อความตาม \(w_i / |m_i|\)

Sliding window สามแบบ

ถ้ามองทั้งหน้าต่าง ตำรามีสามแบบให้เทียบ

ใน Lab 2: บทสนทนาเดียวกัน งบ 400 token สี่วิธี FIFO ทิ้งทั้งโจทย์และการแก้โจทย์ คำตอบจึงมี paper เก่าที่ผู้ใช้สั่งตัดออก การปักหมุดรักษาโจทย์ได้ แต่การแก้โจทย์ที่มาทีหลังยังหาย การให้น้ำหนักเก็บคำสั่งได้ครบ แต่โน้ตยาวหนึ่งฉบับลงงบไม่ได้ จึงได้ 5 จาก 6 ส่วนการสรุปของเก่า จาก 532 token เหลือ 156 ได้ครบ 6 ฉบับ เหมือนใช้ history ทั้งหมด ด้วย token ไม่ถึงครึ่ง

Recursive context decomposition

ทุกวิธีที่ผ่านมายอมรับข้อจำกัดเดียวกัน คือทุกอย่างต้องอัดลงหน้าต่างเดียว ตำราเล่าถึงอีกแนวคิดที่ไม่ยอมรับข้อจำกัดนี้ คือ recursive language model (RLM) ให้ model เรียกตัวเองซ้ำบนข้อมูลทีละส่วน (Roitman 2026, หมวด 18.2.5)

เหมือนอาจารย์ที่ต้องอ่านวิทยานิพนธ์หกร้อยหน้า แบ่งให้ผู้ช่วยสอนสรุปคนละบท แล้วรวมผลเอง ทำไมวิธีนี้ช่วยได้ ตำราอธิบายด้วย context rot คือความแม่นของ model ลดลงเมื่อ context ยาวขึ้น แม้ model จะรับได้ถึง 128K token ก็ตาม การทำให้แต่ละ call สั้นและตรงประเด็นจึงเลี่ยงปัญหานี้ได้ ตำรายกงานวิจัยที่พบว่า GPT-5-mini แบบ recursive ทำได้ดีกว่า GPT-5 แบบธรรมดาในโจทย์ context ยาวที่ยาก และยังถูกกว่าต่อคำถาม

ใน Lab 3: บันทึกการประชุมของกลุ่มวิจัยทั้งปี 52 สัปดาห์ ยาว 8,243 token ซ่อนการตัดสินใจตัด paper ไว้สามจุด เราตั้งงบต่อ call ไว้ 1,500 token (เป็นสมมติฐานของ lab ตัวเอกสารจริงๆ ลง window ของ Gemma ได้สบาย) ตัดให้พอดีแล้วส่งครั้งเดียวเห็นแค่ต้นเอกสาร เจอแค่จุดเดียว recursive_summarize ตามตำราแตกต้นไม้ลึกสองชั้น ใช้ 15 call ใหญ่สุด 798 token ไม่มี call ไหนเกินงบ แต่รอบแรก P04 ไม่มีสัปดาห์ทุกครั้ง เพราะชิ้นย่อยไม่มีบรรทัดหัวข้อ ## Week 27 พอพาหัวข้อไปกับทุกชิ้นก็เจอครบทั้งสามพร้อมสัปดาห์ ชิ้นเล็กแต่ละชิ้นต้องอ่านรู้เรื่องได้ด้วยตัวเอง

Pre-flight token check

ก่อนเรียก LLM ทุกครั้ง harness ต้องทำ checklist สี่ข้อ เหมือน checklist ของนักบินก่อนขึ้นบิน (Roitman 2026, หมวด 18.2.6)

ข้อ ④ ช่วยให้รู้ว่าส่วนไหนกินพื้นที่ ตำราเตือนด้วยว่ากฎ “4 ตัวอักษร ≈ 1 token” อาจเพี้ยนได้ 20–40% สำหรับโค้ด JSON และภาษาที่ไม่ใช่ภาษาอังกฤษ ซึ่งรวมถึงภาษาไทยด้วย

ใน Lab 1: เทียบกับ tokenizer ของ Gemma กฎสี่ตัวอักษรเดาเกินกับภาษาอังกฤษ 19% แต่เดาขาดกับภาษาไทย 32% Python 28% และ JSON 58% พอนับด้วย tokenizer ของ Gemma รวมรูปแบบแชทด้วย เรานับได้ 214 ส่วน API นับได้ 215 ต่างกันแค่หนึ่ง token

Prompt architecture

ตำราบอกว่า prompt คือช่องทางหลักที่ harness ใช้คุยกับ model ควรแยกเป็นส่วนๆ ประกอบกันได้ และมีเวอร์ชันกำกับ (Roitman 2026, หมวด 18.3) system prompt ที่ใช้จริงมักมีสี่ส่วน คือตัวตนของ agent สิ่งที่ทำได้ สิ่งที่ห้ามทำ และรูปแบบคำตอบ โดยเว้นช่องไว้ให้เติมตอนรัน เช่นชื่อ agent รายชื่อ tool หรือวันที่ของวันนี้

harness ไม่เก็บ prompt เป็นข้อความก้อนเดียว แต่ประกอบใหม่ทุกครั้งจากห้า block

\[ \text{Prompt} \;=\; \text{Concat}(\text{System},\ \text{Memory},\ \text{Tools},\ \text{History},\ \text{Query}) \tag{31.4}\]

เหมือนต่อเลโก้ อยากเปลี่ยนก้อนไหนก็ถอดเฉพาะก้อนนั้น และแต่ละก้อนมีเลขเวอร์ชันของมันเอง ตัวอย่าง few-shot ก็อยู่ในงบเช่นกัน ตำราแนะนำให้เลือกเฉพาะตัวอย่างที่คล้ายคำถามตอนนี้ และไม่ให้เกินงบของส่วน \(M\) ส่วนคำอธิบาย tool ที่เราทำแล้วใน EP06 Lab 1 สิ่งที่เพิ่มตอนนี้คือใส่เฉพาะ tool ที่เกี่ยวกับงานตอนนั้น จะได้ประหยัด token และ model สับสนน้อยลง

เขียนเอง vs framework

ใน Lab 4 เราใช้ SummarizationMiddleware ของ LangChain (langchain==1.4.7) ทำสิ่งเดียวกับการสรุปของเก่าที่เขียนเองใน Lab 2

สิ่งที่ framework เพิ่มคือมันตรวจงบเองก่อนเรียก model ทุกครั้ง แต่ prompt ค่าเริ่มต้นเขียนบทสรุปยาว 410 token จนชนเพดาน แล้วต้องสรุปซ้ำแทบทุก turn พอใช้ prompt ของเราจาก Lab 2 ซึ่งได้บทสรุปไม่ถึง 200 token ก็สรุปแค่ครั้งหรือสองครั้ง และได้ครบ 6 ฉบับ framework ช่วยเขียนโค้ด แต่เราต้องรู้ว่าข้างในทำอะไร
