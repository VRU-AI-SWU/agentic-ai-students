วัตถุประสงค์การเรียนรู้

เมื่อจบตอนนี้ ผู้เรียนจะสามารถ

  1. อธิบายว่า LLM สร้างคำตอบทีละ token อย่างไร และ chat template เปลี่ยน messages เป็นสิ่งที่ model อ่านอย่างไร
  2. นับ token ของข้อความไทยและอังกฤษ และประเมินค่าใช้จ่ายของการเรียก model
  3. อธิบาย greedy, top-k, top-p, min-p และ temperature และเลือก temperature ให้เหมาะกับงานของ agent
  4. ใช้ max_tokens และตรวจ finish_reason เพื่อรู้ว่าคำตอบถูกตัดหรือไม่
  5. อ่านชื่อ model (ขนาด, MoE, instruct) และคำนวณหน่วยความจำที่ quantization แต่ละระดับ
  6. อธิบายว่าทำไม model ชื่อเดียวกันจาก provider ต่างกันให้ผลไม่เท่ากัน และเช็ก modality ก่อนส่งรูป

สามคำถามที่คนสร้าง agent เจอ

ทำไมถามคำถามเดียวกันสองครั้งแล้วได้คำตอบไม่เหมือนกัน? ทำไมภาษาไทยเปลืองกว่าภาษาอังกฤษ? และทำไมส่งรูปให้บาง model แล้วพังทันที? คนสร้าง agent ไม่ต้องสร้าง LLM เอง เหมือนคนขับรถไม่ต้องสร้างเครื่องยนต์ แต่ต้อง อ่านหน้าปัดเป็น ตอนนี้เปิดดูหน้าปัดทีละตัว และตอบทั้งสามคำถามด้วยตัวเลขที่รันจริงใน lab

LLM สร้างคำตอบทีละชิ้น

ตำราสรุปการทำงานของ LLM เป็นเส้นทางเดียว (Roitman 2026, หมวด 1.1; Vaswani และคณะ 2017): ข้อความถูกตัดเป็นชิ้นเล็กๆ (token) → model อ่านทุกชิ้นพร้อมกัน → ให้ความน่าจะเป็นกับทุก token ที่อาจมาเป็นตัวถัดไป → เลือกมาหนึ่งตัว แล้วนำไปต่อท้าย input และวนใหม่

เหมือนคีย์บอร์ดมือถือที่แนะนำคำถัดไป แล้วเรากดคำที่แนะนำไปเรื่อยๆ จนจบประโยค ทุกเรื่องในตอนนี้มาจากสองส่วนของเส้นทางนี้: ชิ้นส่วนที่ถูกตัด และ วิธีเลือกชิ้นถัดไป

Token และ chat template

Token คือชิ้นส่วนข้อความที่ model อ่าน ตัวตัดเรียกว่า tokenizer ตำราอธิบายว่าถ้าตัดเป็นตัวอักษร ข้อความจะยาวและคำนวณแพง ถ้าตัดเป็นคำ ก็รับคำใหม่ที่ไม่เคยเห็นไม่ได้ จึงตัดเป็นชิ้นกลางๆ (Roitman 2026, หมวด 1.2; Sennrich และคณะ 2016) เหมือนตัวต่อ Lego: คำที่พบบ่อยอย่าง “the” เป็นชิ้นเดียว ส่วนคำที่หายากประกอบจากชิ้นเล็ก เช่น “unhappiness” อาจเป็น “un” + “happiness”

ตำราแนะนำให้วัด fertility คือจำนวน token ต่อหนึ่งคำ ถ้าสูงแปลว่า tokenizer รองรับภาษานั้นไม่ดี และเพราะราคาคิดเป็น token ภาษาไทยจึงเปลืองกว่า model แต่ละตัวมี tokenizer ของตัวเอง ข้อความเดียวกันจึงนับได้ไม่เท่ากัน

เวลาเรียก model ผ่าน API เราส่ง list ของ messages แต่ละอันมี role บอกว่าใครพูด (system = คำสั่งตั้งต้น, user = ผู้ใช้, assistant = model) แต่ model อ่านได้แค่ token เส้นเดียว chat template จึงเรียง messages เป็นสตริงเดียวและคั่นแต่ละบทด้วย special token เหมือนบทละครที่มีชื่อผู้พูดกำกับไว้ ตำราชี้ว่า token เฉพาะสำหรับเรียก tool น่าเชื่อถือกว่าการให้ model พิมพ์ว่า “now I will call a tool”

ใน Lab 1: ส่งตัวอักษร a ตัวเดียว แต่ usage นับ token เข้ามากกว่าหนึ่ง ส่วนที่เกินคือ token ที่ chat template เติมให้ — 13 token ทุกครั้งที่เรียก และเราจ่ายเงินส่วนนี้ด้วย

ความน่าจะเป็นและ greedy

ทุกครั้งที่จะสร้าง token ใหม่ model ไม่ได้มีคำตอบเดียวในหัว มันให้ความน่าจะเป็นกับทุก token ที่รู้จักรวมกันได้หนึ่ง ตำรายกตัวอย่าง “The capital of France is” ที่ token “Paris” ได้ 0.92 (Roitman 2026, หมวด 1.12) วิธีเลือกที่ง่ายที่สุดคือ greedy: เลือกตัวที่สูงสุดเสมอ เหมือนสั่งเมนูขายดีที่สุดทุกครั้ง ไม่พลาดแต่ไม่เคยได้ลองอะไรใหม่ ตำราเตือนว่ามักได้ข้อความซ้ำและจืด

API ไม่ได้คืนความน่าจะเป็นตรงๆ แต่คืน logprob (log ของความน่าจะเป็น) ซึ่งแปลงกลับได้ด้วย \(p = e^{\text{logprob}}\) เช่น logprob \(-0.28\) คือ \(e^{-0.28} \approx 0.756\)

สุ่มแบบมีขอบเขต: top-k, top-p, min-p

ถ้าอยากได้ความหลากหลายต้อง สุ่ม ตามความน่าจะเป็น แต่ถ้าสุ่มจากทุก token อาจได้คำแปลกๆ หลุดมา จึงต้องตัดหางทิ้งก่อน ตำราเล่าไว้สามวิธี นึกถึงการคัดผู้เข้ารอบประกวดร้องเพลง

ตัวอย่างในตำรา: หลัง “2 + 2 =” token “4” ได้เกือบทั้งหมด top-k ห้าสิบจะเก็บคำตอบผิดไว้อีก 49 ตัว แต่ top-p เหลือแค่ “4” ส่วนหลัง “I enjoy eating” อาหารที่เป็นไปได้มีเยอะ top-k ห้าแคบเกินไป แต่ top-p ขยายกลุ่มให้เอง top-p และ min-p จึงปรับตามความมั่นใจของ model ส่วน top-k ไม่ปรับ (Holtzman และคณะ 2020; Nguyen และคณะ 2025)

Temperature: ปุ่มความกล้า

ก่อนสุ่มยังปรับรูปร่างของความน่าจะเป็นได้ด้วย temperature (\(T\)) ใน Lab 2 เราเขียนเองจากความน่าจะเป็น \(p_i\):

\[ p_i^{(T)} = \frac{p_i^{1/T}}{\sum_j p_j^{1/T}} \tag{1.1}\]

\(T < 1\) ทำให้ตัวที่สูงยิ่งสูง (มั่นใจ) \(T > 1\) ทำให้ทุกตัวเข้าใกล้กัน (กล้าเสี่ยง) และ \(T \to 0\) คือ greedy ตำรายกตัวอย่าง “Once upon a time” ที่ \(T = 0.3\) model เล่าเรื่องพระราชาผู้ทรงธรรมแบบนิทานทั่วไป แต่ที่ \(T = 1\) กลายเป็นแม่น้ำไหลย้อนกลับและปลาหัดบิน และแนะนำ \(T = 0\) สำหรับโค้ดและคณิตศาสตร์, 0.7 สำหรับงานข้อเท็จจริง, 1–1.2 สำหรับงานสร้างสรรค์

สำคัญสำหรับ agent

ตอนที่ model ต้องเขียนชื่อ tool และ argument ให้ถูก ให้ใช้ temperature ต่ำ นี่คือคำตอบของคำถามแรก: ถามซ้ำได้คำตอบไม่เหมือนเดิม เพราะ model สุ่ม เลือก token

ใน Lab 2 (ความน่าจะเป็นจริงของ Gemma ผ่าน provider ที่ล็อกไว้): “The capital of France is” → Paris เกือบ 1.00 · “I enjoy eating” → pizza 0.756, food 0.115, everything 0.105 · ที่ \(T = 2\) pizza เหลือ 0.485 · top-k 5 เก็บแม้แต่ “Paris” ภาษาจีนและญี่ปุ่น แต่ top-p 0.95 เหลือ Paris ตัวเดียว · การตั้ง temperature=0 บน API ได้ pizza ครบ 10 ครั้งจาก 10

Context window และ max_tokens

Context window คือจำนวน token สูงสุดที่ model อ่านและเขียนได้ในครั้งเดียว Gemma 4 26B ที่ใช้ใน lab ได้ 262,144 token ตำราเรียกมันว่าความจำใช้งานของ agent (Roitman 2026, หมวด 18.2): ทุก token ในนั้นมีค่าเงินและเวลา และ token ที่อยู่นอกนั้น model มองไม่เห็นเลย เหมือนโต๊ะทำงานที่เราอ่านได้เฉพาะกระดาษบนโต๊ะ หนังสือในห้องสมุดดีแค่ไหนก็ไม่ช่วยถ้าไม่ได้หยิบมาวาง บนโต๊ะมีทั้งคำสั่งตั้งต้น ประวัติการคุยที่ยาวขึ้นเรื่อยๆ และพื้นที่เผื่อไว้ให้คำตอบ จึงควร นับ token ก่อนส่งทุกครั้ง

ฝั่งคำตอบมีเพดานชื่อ max_tokens ถ้าถึงก่อนพูดจบ คำตอบจะถูกตัดกลางประโยค และ finish_reason จะเป็น "length" แทน "stop"

ใน Lab 1: ถามหนึ่งพันครั้งยังแค่ราวหนึ่งเซนต์ แต่ agent เรียกหลายรอบและส่งประวัติซ้ำ ตัวเลขจึงโตเร็ว และเมื่อตั้ง max_tokens ต่ำ คำตอบถูกตัดจริงพร้อม finish_reason = "length" — agent ต้องเช็กทุกครั้ง

อ่านชื่อ model ให้เป็น

ชื่อบน OpenRouter อย่าง google/gemma-4-26b-a4b-it อ่านได้ทีละส่วน

MoE เหมือนโรงพยาบาลที่มีหมอเฉพาะทางเยอะ แต่คนไข้แต่ละคนพบหมอแค่สองคน ส่วน instruct เหมือนคนที่อ่านหนังสือมามาก แล้วฝึกงานเป็นเจ้าหน้าที่ตอบคำถาม งานของ agent จึงควรใช้รุ่น instruct

Quantization และ provider

model 26 พันล้าน parameter ถ้าเก็บแต่ละตัวเลขด้วย 16 บิต (2 ไบต์) ต้องใช้หน่วยความจำราว 52 GB วิธีที่ตำราบอกว่าใช้เสมอตอนให้บริการ model คือ quantization: ลดจำนวนบิตต่อตัวเลข (Roitman 2026, หมวด 1.14) เหมือนปัด 3.14159 เหลือ 3.14 หรือย่อรูป RAW เป็น JPEG ไฟล์เล็กลงมากแต่ตาแทบมองไม่ต่าง

\[ \text{หน่วยความจำ (GB)} \approx \text{parameter (พันล้าน)} \times \frac{\text{บิต}}{8} \tag{1.2}\]

บริษัทที่รัน model ให้เราเรียกผ่าน API เรียกว่า provider Gemma ชื่อเดียวกันบน OpenRouter มีถึง 15 เจ้า บางเจ้ารันที่ bf16 บางเจ้า fp8 หรือ fp4 และบางเจ้าไม่บอก ราคาและ context window ก็ต่างกัน

ใน Lab 3 (2026-11-09): ราคา token เข้าต่างกันเกือบ 4 เท่า บางเจ้าให้ context แค่ 131,072 token ครึ่งเดียวของเจ้าอื่น และถาม “I enjoy eating” กับ 4 เจ้า ได้ผลไม่เท่ากัน — Google ให้ pizza 0.76 แต่ Darkbloom ให้ food 0.77 จึงควรล็อก provider ไว้ตอนทดสอบ agent ไม่อย่างนั้นผลวันนี้กับพรุ่งนี้อาจมาจากคนละเจ้า

Modality: model รับอะไรได้บ้าง

ชนิดของข้อมูลเรียกว่า modality เช่น ข้อความ รูปภาพ เสียง วิดีโอ หรือไฟล์ model แต่ละตัวรับได้ไม่เหมือนกัน และ input กับ output แยกกัน: Gemma 4 ดูรูปได้แต่วาดรูปไม่ได้ เพราะเกือบทุก model ตอบเป็นข้อความ ตำราเล่มนี้ตั้งใจเน้น model ที่รับและตอบเป็นข้อความ ตัวเลขด้านล่างจึงมาจากรายชื่อบน OpenRouter

รูปก็ถูกแปลงเป็น token จึงกิน context และคิดเงินด้วย และชื่อ model ไม่ได้บอก modality เสมอไป ถ้า tool ของ agent ดึงรูปมาส่งให้ model ต้องเช็ก modality ก่อน ไม่อย่างนั้น agent จะพังกลางทาง

ใน Lab 3: จาก 461 model บน OpenRouter มี 137 ตัวที่รับได้แค่ข้อความ คำถามประโยคเดียวพร้อมรูปกราฟใช้ token เข้า 278 token เพราะรูปถูกแปลงเป็น token (ตัวเลขในกราฟเป็นข้อมูลสมมติเพื่อการสอน)

คำถามทบทวน

  1. ทำไมประโยคไทยกับอังกฤษที่ความหมายเดียวกันจึงใช้ token ไม่เท่ากัน และ model ต่างตัวนับเท่ากันไหม
  2. ส่งข้อความสั้นมากแต่ usage นับ token เข้ามากกว่าที่คิด ส่วนที่เกินมาจากไหน
  3. หลัง “2 + 2 =” ทำไม top-p จึงเหมาะกว่า top-k 50
  4. ถ้า agent ต้องเรียก tool ให้ถูกทุกครั้ง ควรตั้ง temperature อย่างไร เพราะอะไร
  5. finish_reason = "length" บอกอะไร และ agent ควรทำอย่างไร
  6. Gemma 4 26B ที่ fp8 ใช้หน่วยความจำราวเท่าไร คำนวณอย่างไร
  7. ทำไมควรล็อก provider ไว้ตอนทดสอบ agent
  8. ถ้า tool ของ agent ดึงรูปมาส่งให้ model ต้องเช็กอะไรก่อน

อ่านเพิ่มเติม

ไม่จำเป็นต่อการทำ lab แต่ช่วยให้เข้าใจลึกขึ้น เรียงตามหัวข้อในหน้านี้

  • Transformer ต้นฉบับ: paper ที่ทุก LLM ในคอร์สนี้สืบทอดมา (Vaswani และคณะ 2017)
  • Token: วิดีโอที่สร้าง tokenizer แบบ GPT ตั้งแต่ศูนย์ (Karpathy 2024) และ BPE ต้นฉบับ (Sennrich และคณะ 2016) ส่วน chat template ดูได้จากเอกสาร Hugging Face (Hugging Face 2025a)
  • Decoding: บทความที่เทียบ greedy, beam search, top-k, top-p พร้อมโค้ดให้ลอง (Platen 2020) ที่มาของ top-p (Holtzman และคณะ 2020) และ min-p (Nguyen และคณะ 2025)
  • Instruction-tuned: วิธีฝึก base model ให้ทำตามคำสั่ง (InstructGPT) (Ouyang และคณะ 2022)
  • Mixture of experts: บทความอธิบาย MoE เข้าใจง่าย (Hugging Face 2023) และ paper ของ Switch Transformer (Fedus และคณะ 2022) กับ Mixtral (Jiang และคณะ 2024)
  • Quantization: ภาพรวมวิธีต่างๆ ใน Hugging Face (Hugging Face 2025b) และ paper ที่ทำให้รัน model 8 บิตได้แพร่หลาย (Dettmers และคณะ 2022)
